    Python Internals — Study Notes

    Part III: Functions

    Functions are Python's most important building block, and also its most misunderstood object type — first-class values with their own memory model, closures that capture state without classes, and two protocols (generators and iterators) that quietly power every for loop you've ever written.

    Goal of this part Understand functions as real objects with real internal structure — not just "callable blocks of code" — and build a precise mental model of closures, decorators, generators, and iterators: what CPython actually constructs in memory for each, and why they behave the way they do.
    CH. 14First-Class

    Functions

    Part I's object model (Chapter 4) said "everything is an object" — this chapter takes that claim seriously for functions specifically, then works through every parameter-passing shape Python supports, since the flexibility of Python's calling convention is one of its most heavily used, and most heavily misunderstood, features.

    Function objects

    A def statement doesn't just "declare" a function the way it might in a statically compiled language — it executes, at runtime, creating an actual function object and binding it to a name in the enclosing namespace, exactly like any other assignment (Chapter 4).

    python3
    def greet(name):
    return f"Hello, {name}"

type(greet)          # <class 'function'> -- an ordinary object, like any int or list
greet.__name__       # 'greet'
greet.__code__       # the code object (Part I, Ch.2) -- bytecode + metadata
greet.__defaults__   # default argument values, as a tuple
greet.__doc__        # docstring, or None

# Because it's an object, it can be reassigned, stored, passed around freely
say_hi = greet
say_hi("Ada")          # 'Hello, Ada' -- same function object, different name

    Concretely, a function object bundles together the code object from Part I's compilation pipeline, a reference to the global namespace it should run against, default argument values, and (as Chapter 15 covers) any captured closure cells — everything the interpreter needs to create a new frame and execute the function's bytecode on demand.

    Parameters vs arguments

    These two words are often used interchangeably in casual speech, but precisely: a parameter is a name in the function's own definition (def f(x): — x is a parameter); an argument is the actual value supplied at a specific call site (f(5) — 5 is the argument). Every call is Python binding arguments to parameters according to a well-defined matching algorithm, covered piece by piece below.

    Default arguments

    A parameter can specify a default value, used when the caller omits that argument. The critical internal detail: default values are evaluated exactly once, at def-execution time — not on every call — and stored on the function object itself (__defaults__).

    python3
    def log(message, level="INFO"):
    print(f"[{level}] {message}")

log("started")              # [INFO] started
log("failed", "ERROR")      # [ERROR] failed
    The mutable default argument trap, precisely Because the default is computed once at definition time and reused for every call that doesn't override it, a mutable default (a list, dict, or any mutable object) is shared across all calls — exactly the same underlying mechanism flagged in Part II, Chapter 9. The standard fix: default to None, and create the mutable object fresh inside the function body each call. 
    # WRONG -- one shared list across every call
def append_item(item, bucket=[]):
    bucket.append(item)
    return bucket

# RIGHT -- a fresh list every call
def append_item(item, bucket=None):
    if bucket is None:
        bucket = []
    bucket.append(item)
    return bucket

    Keyword arguments

    Any argument can be passed by explicitly naming its parameter at the call site, in any order, as long as every required parameter ends up filled:

    python3
    def connect(host, port, timeout=30):
    ...

connect("localhost", 8080)                       # positional
connect(host="localhost", port=8080)            # keyword, matches positional order
connect(timeout=5, host="localhost", port=8080)  # keyword, ANY order

    Keyword arguments exist primarily for readability at the call site (connect(timeout=5, ...) is self-documenting in a way connect(..., 5) isn't) and to let callers skip earlier optional parameters while still supplying a later one.

    Positional-only parameters

    PEP 570 (Python 3.8) added a / marker in a signature: every parameter before it can only be passed positionally — supplying it by keyword raises TypeError. This exists to let library authors change a parameter's name later without breaking callers who might have passed it by keyword, and to model real built-ins (many of which have always behaved this way internally):

    python3
    def divide(a, b, /, precision=2):
    return round(a / b, precision)

divide(10, 3)                 # fine -- a, b positional
divide(10, 3, precision=4)   # fine -- precision can be keyword
divide(a=10, b=3)             # TypeError -- a, b are positional-only

    Keyword-only parameters

    The mirror image: a bare * in a signature marks every parameter after it as keyword-only — it can never be supplied positionally, forcing callers to name it explicitly, usually to keep less-common options readable and unambiguous:

    python3
    def create_user(name, *, admin=False, active=True):
    ...

create_user("Ada", admin=True)     # fine -- admin passed by keyword
create_user("Ada", True)            # TypeError -- admin is keyword-only, can't be positional

    Both markers can appear in the same signature — def f(a, b, /, c, *, d): — giving fine-grained control: a, b positional-only, c either, d keyword-only, reading left to right exactly as it's declared.

    *args

    *args collects any number of extra positional arguments into a tuple inside the function — the "packing" counterpart to Chapter 8's unpacking star syntax:

    python3
    def total(*numbers):
    return sum(numbers)

total(1, 2, 3, 4)     # 10 -- numbers = (1, 2, 3, 4)

# The star also SPREADS an iterable into positional arguments at a call site
values = [1, 2, 3]
total(*values)          # same as total(1, 2, 3)

    The name args is pure convention, not syntax — *whatever works identically; only the leading * is what matters to the interpreter.

    **kwargs

    **kwargs is the same idea for keyword arguments — it collects any number of extra name=value arguments into a dict inside the function:

    python3
    def build_url(base, **params):
    query = "&".join(f"{k}={v}" for k, v in params.items())
    return f"{base}?{query}"

build_url("/search", q="python", page=2)   # '/search?q=python&page=2'

# And ** SPREADS a dict into keyword arguments at a call site
opts = {"q": "python", "page": 2}
build_url("/search", **opts)

    The full, canonical signature ordering, when all forms are combined, is:

    signature order
    def f(pos_only, /, normal, *args, kw_only, **kwargs):
    ...
# positional-only -> normal (positional-or-keyword) -> *args ->
# keyword-only -> **kwargs -- this exact order is enforced by the grammar
    Chapter 14 — Key takeaways
    • def is an executable statement that builds a real function object at runtime — functions are first-class values, storable and passable like any other object.
    • Default argument values are computed once, at definition time — never use a mutable default; default to None and construct fresh inside the function.
    • / and * in a signature carve it into positional-only, normal, and keyword-only zones, giving API authors precise control over how callers are allowed to pass each argument.
    • *args/**kwargs both pack extra arguments (in a def) and spread existing collections into arguments (at a call site) — same star syntax, opposite direction, context-dependent.
    CH. 15Captured State

    Closures

    Part II, Chapter 6 introduced the LEGB rule and the nonlocal keyword. This chapter opens up the actual mechanism behind the "E" (Enclosing) scope — how a nested function can keep using a variable from its enclosing function after that enclosing function has already returned, which is not at all obvious once you remember that a returned function's frame (Part I, Ch. 5) should normally be garbage-collected.

    Nested functions

    Python allows defining a function inside another function — the inner def executes each time the outer function runs, creating a fresh inner function object every call, exactly as described in Chapter 14:

    python3
    def outer():
    def inner():
        print("hello from inner")
    return inner    # returning the FUNCTION OBJECT itself, not calling it

fn = outer()      # fn now holds the inner function object
fn()              # "hello from inner" -- called later, well after outer() has returned

    On its own this is unremarkable — but it becomes interesting the moment inner references a name from outer's local scope.

    Closures

    A closure is exactly this situation: a nested function that references a name from an enclosing (but not global) scope, and is returned or otherwise escapes that enclosing function — meaning the nested function "closes over" that variable, keeping it alive and accessible for as long as the function itself exists, no matter how long after the outer function has finished running.

    python3
    def make_multiplier(factor):
    def multiply(x):
        return x * factor    # 'factor' is a FREE VARIABLE here -- not local, not global
    return multiply

double = make_multiplier(2)
triple = make_multiplier(3)

double(5)     # 10
triple(5)     # 15 -- a DIFFERENT captured 'factor', from a different call to make_multiplier

    Each call to make_multiplier creates its own independent closure — double and triple each capture a separate factor value, proving that closures capture per-call state, not some single shared slot. This is the standard mechanism behind function factories, and it's the same fundamental idea behind class-based objects with instance state — a closure is, informally, "a poor man's object with exactly one method."

    Free variables

    A free variable is a name used inside a function that is neither a local variable nor a global variable — it belongs to an enclosing function's scope. The compiler (Part I, Ch. 2) statically determines this at compile time by analyzing the nested function's body, and stores the list of such names on the code object:

    python3
    def make_multiplier(factor):
    def multiply(x):
        return x * factor
    return multiply

multiply_fn = make_multiplier(2)
multiply_fn.__code__.co_freevars   # ('factor',) -- confirmed free variable
multiply_fn.__closure__            # (<cell at 0x...: int object at 0x...>,) -- one cell per free variable

    This is a genuinely different lookup mechanism than plain LEGB global lookup — free variables are resolved through the closure mechanism (cells, below) rather than a namespace dictionary lookup, which is a real, measurable performance difference: closure-variable access compiles to dedicated LOAD_DEREF/STORE_DEREF bytecode instructions (Part I, Ch. 3), distinct from the LOAD_FAST/LOAD_GLOBAL instructions used for ordinary locals and globals.

    Cell objects

    Here is the actual mechanism, and it answers the "how does the variable survive after the outer function returns" question directly: whenever the compiler detects a variable is referenced by a nested function, it doesn't store that variable as a plain local — it wraps it in a cell object, a small heap-allocated box that both the outer function's frame and the inner function's closure hold a reference to.

    outer()'s frame (locals)
    factor→ cell ●
    cell object (heap)
    contents2
    multiply's __closure__
    [0]→ same cell ●

    Because it's the cell that's kept alive by reference counting (Part I, Ch. 5) — not the outer frame itself — the cell survives perfectly well after outer() returns and its frame is destroyed, as long as at least one still-alive function object's __closure__ tuple still points at it. This is exactly why closures work at all: the captured variable's storage is fundamentally decoupled from the lifetime of the function call that created it.

    Gotcha: the classic late-binding closure bug Closures capture the cell (a reference to a mutable box), not a frozen snapshot of the value at definition time — so if the same cell is mutated after the closure is created but before it's called, every closure sharing that cell sees the latest value, not the value from when it was defined: 
    # WRONG -- all three closures share the SAME loop variable 'i'
funcs = [lambda: i for i in range(3)]
[f() for f in funcs]    # [2, 2, 2] -- NOT [0, 1, 2]! i's final value, read 3 times

# RIGHT -- default argument captures the value AT DEFINITION TIME instead
funcs = [lambda i=i: i for i in range(3)]
[f() for f in funcs]    # [0, 1, 2] -- each lambda got its own default value, bound once

    nonlocal, revisited

    Part II, Chapter 6 introduced nonlocal as the tool for rebinding an enclosing-scope name from within a nested function. Now the mechanism is fully visible: nonlocal count tells the compiler that assignments to count inside this function should write through to the shared cell, rather than creating a fresh local — which is exactly what makes the classic stateful-counter closure work:

    python3
    def make_counter():
    count = 0              # becomes a cell, because 'increment' below references it
    def increment():
        nonlocal count
        count += 1          # writes through to the SHARED cell -- STORE_DEREF, not STORE_FAST
        return count
    return increment

counter = make_counter()
counter(), counter(), counter()   # (1, 2, 3) -- the cell persists and accumulates across calls

    Without nonlocal, count += 1 would be treated as a fresh local assignment inside increment (per the LEGB rule from Part II, Ch. 6) and raise UnboundLocalError on the read half of +=, because the compiler would never wire up the cell reference in the first place.

    Chapter 15 — Key takeaways
    • A closure is a nested function that captures a free variable from an enclosing scope and keeps working after that enclosing call has returned.
    • The mechanism is a cell object — a heap-allocated box shared by reference between the outer frame and the inner function's __closure__ tuple, kept alive by ordinary reference counting.
    • Closures capture the cell, not a value snapshot — this is the root cause of the classic "all lambdas in a loop return the same value" bug, fixed with a default-argument-capture trick.
    • nonlocal is what tells the compiler to route an assignment through the shared cell instead of creating a new local, enabling stateful closures like counters.
    CH. 16Functional Toolkit

    Lambda & Functional Programming

    Python is not a functional language in the Haskell/ML sense, but it borrows several functional-programming tools that lean heavily on the "functions are objects" property from Chapter 14. This chapter covers the anonymous-function syntax and the small toolkit built around passing functions as values.

    Anonymous functions (lambda)

    lambda creates a function object without a def statement or a name — useful for small, throwaway functions passed directly as arguments where defining a full named function would be needlessly verbose. A lambda is restricted to a single expression (no statements, no multiple lines, no assignments) whose value is implicitly returned.

    python3
    square = lambda x: x ** 2
square(5)                 # 25

# Equivalent def -- lambda is genuinely just sugar for this
def square(x):
    return x ** 2

# Most common real use: as a throwaway "key" function
people = [("Bob", 25), ("Ada", 36), ("Cy", 19)]
people.sort(key=lambda person: person[1])   # sort by age

    A lambda produces the exact same kind of function object as def (Chapter 14) — same type, same closure-capturing behavior (Chapter 15) — its only differences are syntactic: no name (__name__ is literally the string "<lambda>"), and the single-expression-only body restriction.

    Style guidance PEP 8 explicitly discourages name = lambda: ... assignment — if a lambda is important enough to have a name, a regular def gives better tracebacks (a named function shows its real name in stack traces; a lambda always shows <lambda>) and supports docstrings and type annotations. Reserve lambda for genuinely anonymous, inline, throwaway use — almost always as an argument to another function.

    Functional programming in Python

    "Functional" here means treating functions as ordinary values — passing them as arguments, returning them from other functions, and building new behavior by combining them, rather than through explicit loops and mutable state. Chapter 14 (functions as objects) and Chapter 15 (closures) are the two features that make this style possible at all; the rest of this chapter is a tour of the standard tools built on top of them.

    map

    map(func, iterable) applies func to every item of iterable, lazily — it returns an iterator (Chapter 19), not a list, computing each result only as it's requested:

    python3
    nums = [1, 2, 3, 4]
squared = map(lambda x: x ** 2, nums)
squared                     # <map object at 0x...> -- nothing computed yet
list(squared)              # [1, 4, 9, 16] -- computed now, on demand

# map() also accepts multiple iterables, zipping them positionally
list(map(lambda a,b: a+b, [1,2,3], [10,20,30]))   # [11, 22, 33]

    In modern Python style, an equivalent list comprehension ([x**2 for x in nums]) is generally preferred for readability — map remains common mainly when the function being applied already exists as a named function (map(str, nums) reads cleanly) rather than a fresh lambda.

    filter

    filter(predicate, iterable) keeps only the items for which predicate(item) is truthy — also lazy, also returning an iterator:

    python3
    nums = [1, 2, 3, 4, 5, 6]
evens = filter(lambda x: x % 2 == 0, nums)
list(evens)              # [2, 4, 6]

# filter(None, iterable) -- special case: keeps only TRUTHY items
list(filter(None, [0, 1, "", "hi", [], [1]]))   # [1, 'hi', [1]]

    Same readability trade-off as map: [x for x in nums if x % 2 == 0] is the idiomatic equivalent most style guides prefer for simple predicates.

    reduce

    functools.reduce(func, iterable, [initial]) repeatedly applies a two-argument function, carrying an accumulated result forward, collapsing an entire iterable down to a single value — unlike map/filter, it's eager, not lazy, since it must consume the whole iterable to produce its one final result.

    python3
    from functools import reduce

nums = [1, 2, 3, 4]
reduce(lambda acc, x: acc + x, nums)         # 10
reduce(lambda acc, x: acc + x, nums, 100)    # 110 -- starts from an explicit initial value

# Trace: ((((0+1) as acc=1) +2 =3) +3=6) +4=10  -- accumulator carried forward each step
    Why reduce moved to functools reduce was a builtin in Python 2 but was demoted to functools in Python 3 — Guido van Rossum specifically argued that most reduce calls are less readable than an equivalent explicit loop, and that the common cases (sum, max, min, any, all) already have dedicated, clearer builtins. Reach for reduce only when no specialized builtin fits.

    partial

    functools.partial(func, *args, **kwargs) creates a new callable with some arguments pre-filled — "freezing" part of a function's signature to produce a more specialized function, without writing a wrapper def by hand:

    python3
    from functools import partial

def power(base, exponent):
    return base ** exponent

square = partial(power, exponent=2)
cube    = partial(power, exponent=3)

square(5)     # 25  -- equivalent to power(5, exponent=2)
cube(5)       # 125 -- equivalent to power(5, exponent=3)

    Under the hood, partial returns a real object (a functools.partial instance, not a plain function) that stores the original callable plus the pre-bound arguments, and calls the original with the stored arguments merged in whenever it's invoked — a small, explicit, introspectable wrapper rather than a closure built by hand, though a hand-written closure (lambda base: power(base, exponent=2)) achieves much the same effect using exactly the mechanism from Chapter 15.

    Chapter 16 — Key takeaways
    • lambda creates the exact same function object type as def — restricted to a single expression, with no name of its own.
    • map and filter are lazy (return iterators, Chapter 19); reduce is eager (must consume everything to produce its one result).
    • List/generator comprehensions are generally the more idiomatic, more readable alternative to map/filter with a lambda in modern Python.
    • partial pre-binds some arguments of an existing function, producing a new, more specialized callable without hand-writing a wrapper.
    CH. 17★ Metaprogramming

    Decorators

    Decorators are where Chapters 14–16 converge: functions as objects, higher-order functions that take and return other functions, and closures that wrap behavior around existing behavior — combined into one of Python's signature idioms. By the end of this chapter, @decorator syntax should look like exactly what it is: a plain function call in disguise.

    Functions are objects (why this makes decorators possible)

    Chapter 14 established that a def creates a real object. That single fact is the entire foundation decorators are built on: if functions are just objects, then a function can accept another function as an argument and return a function as a result, exactly like any other value.

    Higher-order functions

    A higher-order function is any function that takes a function as an argument, returns a function, or both — map, filter, and sorted(..., key=...) from Chapter 16 already qualify. A decorator is simply a higher-order function that takes one function and returns a (usually different) function:

    python3
    def shout(func):
    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)
        return result.upper()
    return wrapper

def greet(name):
    return f"hello, {name}"

greet = shout(greet)    # manually "decorating" -- rebind greet to the wrapped version
greet("ada")             # 'HELLO, ADA'

    @ syntax is pure sugar for exactly that reassignment pattern:

    python3
    @shout
def greet(name):
    return f"hello, {name}"

# is EXACTLY equivalent to:
#
#   def greet(name):
#       return f"hello, {name}"
#   greet = shout(greet)
#
# The decorator runs once, at DEFINITION time, immediately replacing
# the name 'greet' with whatever shout(greet) returns.

greet("ada")   # 'HELLO, ADA'

    Wrapper functions & closures at work

    The inner wrapper function is a closure (Chapter 15) — it captures func, the original function, as a free variable, which is precisely what lets it call the original function later, inside the new behavior. This is why decorators and closures are inseparable topics: without closures, there would be no way for the returned wrapper to remember which original function to call.

    timing_decorator.py
    import time

def timed(func):
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        result = func(*args, **kwargs)      # call the ORIGINAL function
        elapsed = time.perf_counter() - start
        print(f"{func.__name__} took {elapsed:.4f}s")
        return result                        # pass its result through unchanged
    return wrapper

@timed
def slow_add(a, b):
    time.sleep(0.1)
    return a + b

slow_add(2, 3)   # prints "slow_add took 0.1003s", returns 5

    The *args, **kwargs pattern (Chapter 14) in the wrapper is what lets a single decorator work on functions with any signature — the wrapper doesn't need to know or care what arguments the wrapped function takes; it just forwards everything through transparently.

    Decorators that take their own arguments need one more level of nesting — a function that returns a decorator, which returns a wrapper:

    python3
    def retry(times):              # outer: takes the decorator's OWN arguments
    def decorator(func):        # middle: takes the function being decorated
        def wrapper(*args, **kwargs):  # inner: the actual replacement function
            for attempt in range(times):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    print(f"Attempt {attempt+1} failed: {e}")
            raise RuntimeError("All retries failed")
        return wrapper
    return decorator

@retry(times=3)
def flaky_call():
    ...

# @retry(times=3) is a CALL that returns 'decorator', which then
# decorates flaky_call -- three levels of function, three levels of closure

    Metadata & functools.wraps

    There's a real cost to the naive wrapper pattern above: once greet is replaced by wrapper, introspection tools see the wrapper's identity, not the original function's — greet.__name__ becomes "wrapper", its docstring disappears, and tools like debuggers, help(), and documentation generators lose the real function's identity entirely.

    python3
    @timed
def slow_add(a, b):
    """Add two numbers slowly."""
    ...

slow_add.__name__   # 'wrapper'  -- WRONG, lost the real name
slow_add.__doc__    # None       -- WRONG, lost the docstring

    functools.wraps fixes this — it's itself a decorator (applied to the wrapper, inside your decorator's own definition) that copies over __name__, __doc__, __module__, and other metadata from the original function onto the wrapper, and also sets wrapper.__wrapped__ = func so the original is still reachable:

    python3
    import functools

def timed(func):
    @functools.wraps(func)     # the fix -- always do this in real decorators
    def wrapper(*args, **kwargs):
        ...
        return func(*args, **kwargs)
    return wrapper

@timed
def slow_add(a, b):
    """Add two numbers slowly."""
    ...

slow_add.__name__   # 'slow_add' -- correct now
slow_add.__doc__    # 'Add two numbers slowly.' -- correct now
    Rule of thumb Every decorator you write that defines an inner wrapper should apply @functools.wraps(func) to that wrapper — there's essentially no downside, and skipping it silently degrades debugging, introspection, and any tooling that relies on accurate function metadata.

    functools essentials

    Beyond wraps, reduce, and partial (Chapter 16), the functools module ships several decorators worth knowing directly:

    @functools.lru_cache
    Memoizes a function's return values keyed by its arguments — repeat calls with the same arguments return the cached result instantly instead of recomputing. maxsize= bounds the cache (evicting least-recently-used entries); maxsize=None means unbounded.
    @functools.cache
    Python 3.9+ shorthand for lru_cache(maxsize=None) — an unbounded, simpler-to-spell cache.
    @functools.singledispatch
    Turns a function into a generic function that dispatches to different implementations based on the type of its first argument — a lightweight form of function overloading, registered incrementally with @func.register.
    @functools.total_ordering
    A class decorator (see below) — given just __eq__ and one of __lt__/__le__/__gt__/__ge__, fills in the rest of the comparison methods automatically.
    python3
    import functools

@functools.lru_cache(maxsize=128)
def fib(n):
    if n < 2: return n
    return fib(n-1) + fib(n-2)

fib(35)   # fast -- each unique n computed only once, ever, across all calls
fib.cache_info()    # CacheInfo(hits=.., misses=.., maxsize=128, currsize=..)

    Class decorators

    Decorator syntax isn't limited to functions — a @decorator above a class statement works identically: the decorator receives the newly-created class object and returns whatever should be bound to that class's name, exactly the same substitution pattern as with functions.

    python3
    def add_repr(cls):
    def __repr__(self):
        return f"{cls.__name__}({self.__dict__})"
    cls.__repr__ = __repr__     # mutate the class in place...
    return cls                  # ...and return the SAME class object

@add_repr
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

repr(Point(1, 2))   # "Point({'x': 1, 'y': 2})"

    The built-in @dataclass (from the dataclasses module) is the most widely used class decorator in modern Python — it inspects a class's type-annotated attributes and automatically generates __init__, __repr__, and __eq__ for you, eliminating a large amount of boilerplate for simple data-holding classes:

    python3
    from dataclasses import dataclass

@dataclass
class Point:
    x: int
    y: int

p = Point(1, 2)
p               # Point(x=1, y=2) -- __repr__ generated automatically
p == Point(1, 2)   # True -- __eq__ generated automatically too

    A class decorator differs from a class returning a modified instance (which would be normal method logic) in one key way: it operates on the class itself, at class-definition time — capable of adding methods, wrapping every method, registering the class somewhere, or even substituting an entirely different class or object in its place.

    Chapter 17 — Key takeaways
    • @decorator is sugar for name = decorator(name), executed once at definition time — nothing more mysterious than a higher-order function call.
    • The inner wrapper is a closure over the original function; *args, **kwargs lets one decorator wrap functions of any signature.
    • Decorators that take their own arguments need a third level of nesting: args → decorator → wrapper.
    • Always apply @functools.wraps(func) inside a decorator, or the wrapped function silently loses its name, docstring, and other metadata.
    • lru_cache/cache, singledispatch, and total_ordering are the highest-value ready-made decorators in functools.
    • Class decorators work identically to function decorators, just operating on a class object — @dataclass is the most common one in modern code.
    CH. 18Lazy Execution

    Generators

    Every function studied so far runs top to bottom and returns exactly once. This chapter covers a fundamentally different kind of function — one that can pause mid-execution, hand a value back to its caller, and later resume from exactly where it left off, with all of its local state intact.

    yield

    Any function containing a yield statement anywhere in its body is, by that fact alone, a generator function — calling it doesn't run any of its code immediately; it returns a generator object instead, and the function body only starts executing once you start pulling values from that object.

    python3
    def count_up_to(n):
    i = 1
    while i <= n:
        yield i     # pause here, hand 'i' back to the caller
        i += 1       # resumes here, next time a value is requested

gen = count_up_to(3)
gen                    # <generator object count_up_to at 0x...> -- nothing has run yet

next(gen)              # 1 -- runs up to the first yield, then pauses
next(gen)              # 2 -- resumes right after the yield, runs to the next one
next(gen)              # 3
next(gen)              # StopIteration -- loop condition false, function returns, generator is exhausted

    The most common usage pattern doesn't call next() manually at all — a for loop does it automatically (Part II, Ch. 13), calling next() repeatedly and catching StopIteration for you:

    python3
    for num in count_up_to(3):
    print(num)      # 1, 2, 3 -- one per line

    Lazy evaluation

    The defining benefit of generators is laziness: values are produced one at a time, on demand, rather than all at once up front. This means a generator can represent — and efficiently iterate — sequences that would be impossible or wasteful to materialize as a full list:

    python3
    def read_large_file(path):
    with open(path) as f:
        for line in f:
            yield line.strip()
# Processes one line at a time -- memory usage stays flat even for a
# 50 GB file, because the whole file is never loaded into a list at once.

def naturals():
    n = 1
    while True:
        yield n
        n += 1
# An INFINITE sequence -- perfectly fine as a generator, would be
# impossible to represent as an actual list.

    Generator expressions offer the same laziness with comprehension-like syntax — just swap the square brackets for parentheses:

    python3
    squares_list = [x**2 for x in range(1000000)]   # builds the FULL list in memory now
squares_gen  = (x**2 for x in range(1000000))   # builds NOTHING yet -- lazy

sum(squares_gen)   # computed lazily, one value at a time, as sum() consumes it

    Generator objects

    What actually gets paused and resumed is a real, heap-allocated object — a generator holds onto its own frame (Part I, Ch. 5) between calls, rather than that frame being destroyed on return the way an ordinary function's frame is. This is the entire mechanism, made concrete: a generator is a function whose frame CPython keeps alive and re-enters, instead of discarding after a single run.

    python3
    gen = count_up_to(3)
gen.gi_frame       # the actual, currently-suspended frame object
gen.gi_running     # False -- True only WHILE a next()/send() call is actively executing it
next(gen)
gen.gi_frame.f_lasti   # the exact bytecode offset execution is paused at

    This is also why a generator object is itself an iterator (Chapter 19) — it implements __iter__ (returning itself) and __next__ (resuming the frame until the next yield or a return/fall-off-the-end, which raises StopIteration).

    send()

    yield isn't only an exit point — it's also an expression that can receive a value pushed into the generator from outside, via gen.send(value). This makes communication genuinely bidirectional, turning a generator into something closer to a lightweight coroutine:

    python3
    def echo():
    while True:
        received = yield          # pauses here; the SENT value becomes this expression's result
        print(f"got: {received}")

gen = echo()
next(gen)              # REQUIRED "priming" call -- advances to the first yield
gen.send("hello")     # prints "got: hello" -- resumes, 'received' = "hello"
gen.send("world")     # prints "got: world"
    Gotcha A freshly created generator must be advanced once with next(gen) (or gen.send(None), which is equivalent) before you can meaningfully send() a real value — you can't send a value into a generator that hasn't reached its first yield yet; doing so raises TypeError.

    throw()

    gen.throw(exc_type) raises an exception at the point where the generator is currently paused — as if that yield expression itself had raised it — letting the generator's own try/except logic handle cleanup or react to external signals:

    python3
    def resilient():
    while True:
        try:
            yield "working"
        except ValueError:
            print("recovered from ValueError, continuing")

gen = resilient()
next(gen)                    # 'working'
gen.throw(ValueError)         # prints "recovered..." -- caught INSIDE the generator, execution continues

    close()

    gen.close() raises GeneratorExit at the generator's current suspension point, which is the signal for it to run any cleanup code (typically in a finally block) and then stop — after close(), the generator is permanently exhausted, and any further next() call raises StopIteration.

    python3
    def managed_resource():
    print("acquiring")
    try:
        yield "resource"
    finally:
        print("releasing")   # guaranteed to run, even on close() or garbage collection

gen = managed_resource()
next(gen)          # prints "acquiring", yields "resource"
gen.close()         # prints "releasing" -- finally block runs in response to GeneratorExit

    This finally-based cleanup also runs automatically if a generator is simply garbage collected while still suspended (Part I, Ch. 5's reference counting takes care of calling close() as part of destruction) — which is why generator-based resource management (a pattern also underlying @contextlib.contextmanager) is considered safe even if a caller never explicitly finishes iterating.

    Chapter 18 — Key takeaways
    • Any function with yield in its body becomes a generator function — calling it produces a generator object without running any code yet.
    • A generator is, mechanically, a persistent frame CPython keeps alive and re-enters across next() calls, rather than discarding after one run.
    • Laziness is the core value proposition — process infinite or huge sequences with flat, constant memory use.
    • send(), throw(), and close() turn a generator into a two-way communication channel — values in via send, exceptions in via throw, guaranteed cleanup via close and finally.
    CH. 19Protocol

    Iterators

    Chapter 18's generators are, it turns out, just one specific implementation of a much more general protocol — the same protocol that makes for loops, unpacking (Part II, Ch. 8), and comprehensions all work uniformly across lists, dicts, files, and custom objects alike. This closing chapter names that protocol explicitly.

    Iterable vs Iterator — a distinction worth being precise about

    These two words are related but describe different roles, and confusing them is a common source of misunderstanding:

    Iterable
    Any object you can iterate over — anything implementing __iter__, which returns a fresh iterator each time it's called. Lists, dicts, strings, sets, and files are all iterable. An iterable can be iterated over multiple times, independently — each iter(my_list) call gets its own fresh starting point.
    Iterator
    The object that actually does the iterating — implementing both __iter__ (returning itself) and __next__ (producing the next value, or raising StopIteration when exhausted). An iterator is single-use and stateful — once exhausted, it stays exhausted; you can't rewind it.
    python3
    nums = [1, 2, 3]      # nums is ITERABLE -- has __iter__
iter(nums)                # <list_iterator object> -- a fresh ITERATOR, has __next__

it1 = iter(nums)
it2 = iter(nums)
next(it1); next(it1)    # it1 has advanced two steps
next(it2)                # it2 is INDEPENDENT -- still only one step in

# A list is iterable but NOT itself an iterator -- it has no __next__:
next(nums)                # TypeError: 'list' object is not an iterator

    Every iterator is also, trivially, an iterable (its __iter__ just returns itself) — but not every iterable is an iterator. A list is the clearest example of the difference: it's iterable, but you must call iter() on it to get something you can actually call next() on.

    iter()

    The builtin iter(obj) is what a for loop calls implicitly, exactly once, at the very start of iteration. It works by calling obj.__iter__() — and there's a lesser-known second form: iter(callable, sentinel), which repeatedly calls callable() until it returns a value equal to sentinel, useful for reading from things like a file or socket in fixed chunks until a stop marker appears:

    python3
    # Two-argument iter() -- call a function repeatedly until it returns the sentinel
with open("data.bin", "rb") as f:
    for chunk in iter(lambda: f.read(1024), b""):
        process(chunk)
    # stops automatically once f.read(1024) returns b"" (empty bytes = sentinel)

    next()

    next(it) calls it.__next__(), producing the next value or propagating StopIteration when the iterator is exhausted. It accepts an optional second argument as a default, returned instead of letting StopIteration propagate:

    python3
    it = iter([1, 2])
next(it)          # 1
next(it)          # 2
next(it)          # StopIteration -- raised, uncaught

it2 = iter([1])
next(it2, "done")   # 1
next(it2, "done")   # 'done' -- default returned instead of raising

    The iterator protocol, implemented by hand

    Since the protocol is just two dunder methods, any custom class can participate — this is exactly what makes user-defined classes work seamlessly with for loops, list(), unpacking, and every other iteration context in the language:

    custom_iterator.py
    class CountUpTo:
    """Iterable AND iterator in one class -- a common, simple pattern."""
    def __init__(self, n):
        self.n = n
        self.i = 0

    def __iter__(self):
        return self          # the class IS its own iterator

    def __next__(self):
        if self.i >= self.n:
            raise StopIteration    # the REQUIRED signal that iteration is done
        self.i += 1
        return self.i

for num in CountUpTo(3):
    print(num)      # 1, 2, 3

    This is precisely what a for loop does mechanically, spelled out — the exact desugaring, tying directly back to Part II, Chapter 13:

    what "for x in obj:" really does
    _iterator = iter(obj)
while True:
    try:
        x = next(_iterator)
    except StopIteration:
        break
    # ... loop body using x ...

    Generator vs Iterator

    Every generator is an iterator (it implements both dunders, as Chapter 18 noted) — but writing a generator with yield is a vastly more convenient way to get one than hand-rolling a class like CountUpTo above. The comparison:

    Hand-written iterator (class)Generator (yield)
    DefinitionA class with __iter__ + __next__, manual state tracking (self.i, etc.)A function with yield — state is just ordinary local variables, automatically preserved by the paused frame
    VerbosityMore boilerplate — explicit state fields, explicit StopIterationMinimal — the function body reads like a normal, linear algorithm
    Two-way communicationPossible, but must be built by hand (extra methods)Built in — send(), throw(), close() (Chapter 18)
    When to prefer itWhen you need more than one method, custom __iter__ behavior distinct from iteration itself, or non-generator-expressible controlThe default choice for the overwhelming majority of custom iteration needs

    In practice: reach for a generator function first, every time, unless you have a specific reason a plain class serves better — the boilerplate reduction is substantial and the resulting code is almost always easier to read and maintain.

    Tying Part III together The through-line across this entire part: functions are objects (Ch. 14) → closures let them carry state (Ch. 15) → higher-order functions compose them (Ch. 16) → decorators wrap them (Ch. 17) → generators are functions that pause and resume via a persistent frame (Ch. 18) → and that pause/resume capability turns out to be a specific, convenient implementation of the general two-method iterator protocol (Ch. 19) that quietly underlies every for loop in the language.
    Chapter 19 — Key takeaways
    • Iterable = has __iter__, can produce a fresh iterator repeatedly. Iterator = has both __iter__ and __next__, is single-use and stateful.
    • for x in obj: desugars to calling iter(obj) once, then next() repeatedly until StopIteration — this is the exact mechanism, not an approximation.
    • Any class can implement the two-method protocol by hand to become iterable; a generator function gets you the same result with dramatically less code.
    • Prefer generators over hand-written iterator classes by default — reach for a class only when you need capabilities a generator genuinely can't express.
