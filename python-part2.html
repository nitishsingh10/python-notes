    Python Internals — Study Notes

    Part II: Core Python Language

    The building blocks you use in every single Python program — assignment and unpacking, the full type system with its real memory costs, strings and text encoding, the collections that do the heavy lifting, and the control-flow constructs that shape execution.

    Goal of this part Move from "I know the syntax" to "I know what each construct actually costs and why it behaves the way it does" — for every core data type, know its internal representation, its time complexity, and its sharpest gotchas, not just its API.
    CH. 08Foundations

    Variables & Assignment

    Part I, Chapter 4 established that assignment is always a binding, never a copy. This chapter builds on that foundation to cover every shape assignment can take in Python — several of which don't exist in most other languages at all.

    Multiple assignment

    Python allows one expression to be bound to several names in one statement, and several expressions to several names in one statement:

    python3
    # Same object bound to three names
a = b = c = 0
print(a is b is c)   # True -- all three point at the SAME int object

# Different objects, one per name, evaluated left-to-right on the RHS first
x, y, z = 1, 2, 3
    Gotcha with mutable objects a = b = [] binds both names to the same single list — mutating through a is visible through b, because there was only ever one object created. This is a direct, and frequently-tripped-over, consequence of Chapter 4's binding model: the chained form only creates one object on the right, no matter how many names are chained.

    Tuple unpacking

    Python evaluates the right-hand side into a sequence first, then unpacks it positionally into the names on the left — this works for any iterable, not literally just tuples, and the parentheses around a tuple are optional in most positions:

    python3
    point = (3, 4)
x, y = point            # x=3, y=4

# Works on any iterable, including generators and strings
a, b, c = "xyz"          # a='x', b='y', c='z'
first, second = [10, 20]

# The count must match exactly, or ValueError is raised
a, b = (1, 2, 3)         # ValueError: too many values to unpack

    This is also how for loops destructure pairs, which is why for k, v in mydict.items(): reads naturally — each iteration produces a 2-tuple, unpacked directly into k and v.

    Extended (starred) unpacking

    PEP 3132 added a *name form that captures "everything else" as a list, letting you unpack sequences of unknown or variable length without slicing manually:

    python3
    first, *rest = [1, 2, 3, 4]
# first = 1, rest = [2, 3, 4]  -- rest is always a list, regardless of input type

*init, last = [1, 2, 3, 4]
# init = [1, 2, 3], last = 4

first, *middle, last = [1, 2, 3, 4, 5]
# first = 1, middle = [2, 3, 4], last = 5

# Only ONE starred name is allowed per unpacking -- the position is
# unambiguous only if there's a single "everything else" collector.

    The same star syntax appears in function signatures (def f(*args, **kwargs)) and call sites (f(*iterable)) — all three uses share the same underlying idea of "spread or gather a variable number of items," but the assignment-target form above is specifically an unpacking pattern, distinct from the packing behavior in a function definition.

    Swapping without a temp variable

    Python's tuple packing/unpacking combine to make variable swaps a one-liner, with no temporary variable required:

    python3
    a, b = 1, 2
a, b = b, a
print(a, b)   # 2 1

    Mechanically, the right-hand side b, a is fully evaluated into a temporary tuple first — before any assignment on the left happens — and that tuple is then unpacked into a, b. This is why it's safe and correct even for arbitrarily long chains: a, b, c = c, a, b works for exactly the same reason, with no risk of reading a partially-updated value mid-swap.

    The walrus operator (:=)

    PEP 572 (Python 3.8) introduced the assignment expression — written name := expr — which does something ordinary = cannot: it assigns a value and produces that value as the result of an expression, so it can be used inside another expression (an if condition, a comprehension, a while condition) rather than only as a standalone statement.

    python3
    # Before: compute twice, or compute-then-check in two statements
data = fetch()
if data is not None:
    process(data)

# With walrus: compute and check in one expression, no repetition
if (data := fetch()) is not None:
    process(data)

# Very common in comprehensions -- avoids calling an expensive function twice
results = [y for x in data if (y := expensive(x)) is not None]

# Common in while loops reading a stream
while (chunk := file.read(8192)):
    process(chunk)
    Gotcha: not a statement name := expr must appear as part of a larger expression — bare x := 5 as a standalone statement is a SyntaxError (use plain x = 5 for that); and it must always be wrapped in parentheses when used as an if/while condition combined with other operators, to avoid ambiguity with normal =.

    Destructuring, more broadly

    "Destructuring" is the general term for pulling a compound value apart into individual names in one step — Python supports it in more places than plain assignment:

    Nested unpacking
    (a, (b, c)) = (1, (2, 3)) — unpacking patterns can nest arbitrarily to match nested structure.
    In for loops
    for key, (x, y) in points.items(): — each iterated item is unpacked using the same rules as assignment.
    In function parameters
    Python 3 removed implicit tuple-parameter unpacking (it existed in Python 2), so destructuring in a signature must be done explicitly inside the function body today.
    In match statements
    Structural pattern matching (Chapter 13) is a considerably more powerful generalization of destructuring — it can match on type, structure, and value simultaneously, not just position.
    Chapter 8 — Key takeaways
    • Chained assignment (a = b = x) binds every name to one shared object — dangerous with mutable objects, harmless with immutable ones.
    • Unpacking works on any iterable, evaluates the right-hand side fully before binding anything on the left, and requires an exact length match unless a starred target is present.
    • Swapping needs no temp variable because the RHS tuple is built completely before any target is assigned.
    • The walrus operator (:=) assigns and yields a value in one expression — useful for avoiding repeated computation inside conditions and comprehensions.
    CH. 09★ Type System

    Python Data Types

    This is the chapter that turns "I know how to use a list" into "I know what a list costs." For each type below you'll get five things: how CPython actually represents it in memory, the real time complexity of its common operations, its memory footprint, the operations you'll use daily, and the gotchas that trip up even experienced engineers.

    Why immutable vs mutable is the first split that matters Every type in this chapter is either immutable (its value can never change after creation — any "modification" actually produces a brand-new object) or mutable (it can be changed in place, keeping the same identity). This single property determines whether a type can be a dict key or set member (immutability is required, because hash values must stay stable for an object's lifetime), whether it's safe to share across threads without locking, and whether passing it to a function risks the caller seeing changes.

    Immutable types

    Immutable objects can be freely shared — by multiple names, across threads, as dict keys — because nothing can ever change their value out from under a holder. CPython exploits this aggressively for caching and interning, which shows up repeatedly below.

    int
    immutable
    Internal representation

    CPython integers are arbitrary-precision — there's no 32/64-bit overflow, ever. A PyLongObject stores a sign and an array of "digits" in base 2³⁰ (on most 64-bit builds), so a huge integer is really a little array, much like manual long-arithmetic on paper but in base ~1 billion instead of base 10.

    Time complexity
    OperationComplexity
    Add / subtract / compareO(n) in digit count — O(1) for typical small ints
    MultiplyO(n·m) naively; CPython uses Karatsuba for very large operands
    Division / moduloO(n²)-ish for big numbers; effectively O(1) for machine-word-sized ints
    Memory layout

    Header (refcount + type pointer) + size/sign field + inline digit array. A small int on a typical 64-bit build costs around 28 bytes regardless of "smallness" — there's no packed unboxed form. CPython pre-allocates and caches every integer from -5 to 256 as a permanent singleton, so small-int arithmetic in a hot loop reuses existing objects instead of allocating.

    Common operations
    • + - * // % **, bitwise & | ^ ~ << >>
    • int(x), x.bit_length(), x.to_bytes() / int.from_bytes()
    Gotchaa = 200; b = 200; a is b is unreliable — True at the REPL for the -5..256 cache range, but not guaranteed across all contexts, and definitely False for larger numbers each created independently. Never use is for integer value comparison — always ==. Also: / always produces a float (true division); use // for integer floor division.
    float
    immutable
    Internal representation

    A thin wrapper around a native C double — IEEE 754 binary64. Unlike int, there is no arbitrary-precision fallback; a float has a fixed 53 bits of mantissa precision regardless of how it's written in source.

    Time complexity
    OperationComplexity
    Arithmetic, comparisonO(1) — a single hardware FPU instruction
    Memory layout

    Header + one 8-byte double ≈ 24 bytes total. No small-value caching like int — every float literal generally produces its own object (CPython does maintain an internal free list to speed up allocation/deallocation churn, but that's a performance detail, not an identity guarantee).

    Common operations
    • + - * / // % **, round(x, n), math module functions
    • x.is_integer(), float('inf'), float('nan')
    Gotcha0.1 + 0.2 == 0.3 is False — binary floating point cannot represent most decimal fractions exactly, so tiny representation errors accumulate. Compare floats with a tolerance (math.isclose()), never ==. Also: float('nan') == float('nan') is False by IEEE 754 definition — NaN is never equal to anything, including itself.
    bool
    immutable
    Internal representation

    bool is a subclass of int — not a distinct primitive at all. There are exactly two bool instances ever, True and False, permanent singletons living at fixed addresses for the life of the process.

    Time complexity
    OperationComplexity
    EverythingO(1) — same as int, since it is int under the hood
    Memory layout

    Identical struct layout to int; True stores the value 1, False stores 0. No extra allocation ever happens for a boolean — every True anywhere in your program is the exact same object.

    Common operations
    • and or not, comparisons that naturally produce a bool
    • bool(x) — truthiness coercion via __bool__/__len__
    GotchaTrue + True == 2 and isinstance(True, int) is True — because bool really is int. This lets sum(bool_list) count True values, a common (and legitimate) idiom, but it also means {True: 'a', 1: 'b'} is a one-entry dict — True and 1 hash identically and compare equal, so the second assignment overwrites the first.
    complex
    immutable
    Internal representation

    A PyComplexObject holding exactly two C doubles — real and imaginary parts. No arbitrary precision, same IEEE 754 caveats as float apply to each component independently.

    Time complexity
    OperationComplexity
    ArithmeticO(1) — a handful of float ops per operation
    Memory layout

    Header + two 8-byte doubles ≈ 32 bytes.

    Common operations
    • Literal suffix j: 3 + 4j
    • .real, .imag, abs() for magnitude, cmath module for complex-aware sqrt, exp, etc.
    GotchaComplex numbers have no ordering — 1+2j < 3+4j raises TypeError, since "less than" isn't mathematically well-defined on the complex plane. Rare in general application code; common in scientific/DSP work.
    str
    immutable
    Internal representation

    Since PEP 393 (Python 3.3+), CPython uses a "flexible string representation": each string is stored internally using the smallest fixed-width encoding that can hold its widest character — 1 byte/char (Latin-1) if every character fits in 0–255, 2 bytes/char (UCS-2) if the widest character needs up to 0xFFFF, or 4 bytes/char (UCS-4) if any character is outside the Basic Multilingual Plane (e.g. many emoji). This is decided once, at creation, per string.

    Time complexity
    OperationComplexity
    Indexing s[i]O(1) — fixed-width internal storage makes this true random access
    SlicingO(k) for slice length k — copies
    Concatenation s1 + s2O(n+m) — always builds a new string
    in substring searchO(n·m) worst case (CPython uses a Boyer-Moore-ish algorithm in practice)
    Memory layout

    Header + length + a cached hash value (computed once, reused forever — this is why strings make fast dict keys) + the inline character buffer at whichever width PEP 393 selected.

    Common operations
    • Full method set: .split(), .join(), .replace(), .strip(), .format(), f-strings (all covered in depth in Chapter 10)
    GotchaBuilding a large string with repeated s += chunk in a loop is O(n²) overall — each += allocates an entirely new string and copies everything so far, because strings are immutable. Use "".join(chunks) instead, which allocates the final buffer once.
    tuple
    immutable
    Internal representation

    A fixed-size, contiguous C array of PyObject* pointers — essentially the simplest possible container. Size is fixed permanently at creation; there is no over-allocation because a tuple, unlike a list, never needs to grow.

    Time complexity
    OperationComplexity
    IndexingO(1)
    ConcatenationO(n+m) — builds a new tuple
    inO(n) — linear scan
    Memory layout

    Header + length + a tightly-packed pointer array with zero spare capacity — the most memory-efficient general container CPython has. The empty tuple () is a cached singleton.

    Common operations
    • Packing/unpacking (Chapter 8), used as dict keys and set members when all elements are hashable
    • collections.namedtuple / typing.NamedTuple for field-named tuples
    GotchaImmutability is shallow: t = ([1,2], 3) — you can never make t point at a different list, but t[0].append(4) works fine, because the list itself is still mutable. A tuple containing a mutable element is also unhashable, so it can't be used as a dict key. And don't forget the trailing comma for a one-element tuple: (1,), not (1) (which is just the int 1 in parentheses).
    bytes
    immutable
    Internal representation

    A fixed-length, immutable array of raw byte values (each 0–255) — structurally similar to the old pre-PEP-393 string representation, but explicitly for binary data with no encoding interpretation attached.

    Time complexity
    OperationComplexity
    Indexing, slicing, concatenationSame profile as str — O(1), O(k), O(n+m) respectively
    Memory layout

    Header + length + inline byte buffer, exactly 1 byte per element — no width selection needed since there's no character concept, only raw values.

    Common operations
    • .decode(encoding) → str; str.encode(encoding) → bytes (Chapter 10)
    • .hex(), bytes.fromhex(), slicing, used throughout networking and file I/O in binary mode
    GotchaIndexing a bytes object returns an int, not a length-1 bytes: b'abc'[0] is 97, not b'a' (slicing, b'abc'[0:1], does return bytes). Also: bytes and str are never automatically compatible — concatenating or comparing them across types raises TypeError, forcing explicit encode/decode at the boundary.
    frozenset
    immutable
    Internal representation

    The immutable counterpart to set — same open-addressing hash table internals under the hood, just with the "add/remove" operations removed from its API and, crucially, with a working __hash__ restored (regular set deliberately has none).

    Time complexity
    OperationComplexity
    Membership (in)O(1) average
    Union / intersection / differenceO(len(smaller set)) roughly
    Memory layout

    A sparse hash table sized to keep the load factor low (typically resized to stay below ~⅔ full), trading memory for fast average-case lookups — same strategy as set, covered in more depth there.

    Common operations
    • | & - ^ for union/intersection/difference/symmetric-difference
    • Using a frozenset as a dict key or as an element of another set — impossible with a plain set
    GotchaThere is no literal syntax for frozenset — unlike set's {1, 2, 3}, you must always call frozenset(...) explicitly. And every element inside it must itself be hashable, for the same reason tuple elements must be for the tuple to be hashable.

    Mutable types

    Mutable objects can change value in place while keeping the same identity — efficient for building up and modifying data, but unsafe as dict keys (a changing hash would corrupt the hash table) and something to watch for whenever an object is shared across names, function calls, or threads.

    list
    mutable
    Internal representation

    A dynamic array of PyObject* pointers — conceptually identical to a C++ std::vector<void*>. CPython over-allocates the backing array beyond the current element count, so repeated appends don't need to reallocate every single time.

    Time complexity
    OperationComplexity
    Index / index-assignO(1)
    .append(x)Amortized O(1) — occasional O(n) reallocation, averaged out
    .insert(0, x) / .pop(0)O(n) — every later element must shift
    .pop() (from end)O(1)
    in, linear searchO(n)
    .sort()O(n log n) — Timsort, stable
    Memory layout

    Header + a used-length field + an allocated-capacity field + the pointer array itself. Growth roughly follows a ~1.125× pattern (plus a small constant) rather than doubling, tuned empirically by the CPython team to balance wasted memory against reallocation frequency.

    Common operations
    • .append(), .extend(), .insert(), .remove(), .pop(), slicing, list comprehensions
    GotchaThe classic mutable default argument bug: def f(x=[]): — the list is created once, when the function is defined, and reused across every call that doesn't pass its own x, so appends accumulate silently across unrelated calls. Always default to None and create the list inside the function body instead. Also: new = old aliases the same list (Chapter 4); use old.copy() or old[:] for an independent shallow copy.
    dict
    mutable
    Internal representation

    A hash table — but since Python 3.6/3.7 (a de facto implementation detail promoted to a language guarantee in 3.7), CPython uses a "compact dict" design with two arrays instead of one: a sparse array of small integer indices (the actual hash table), and a dense array holding the real entries (hash, key, value) in insertion order. Lookups hash the key, probe the sparse index array to find which slot in the dense array holds it, then read that slot directly — this design is also why iteration order now reliably matches insertion order, essentially for free.

    Time complexity
    OperationComplexity
    Get / set / delete by keyAverage O(1); worst case O(n) under heavy hash collisions
    IterationO(n), in insertion order
    Memory layout

    The sparse index array is sized as a power of two and kept well below full to minimize probing; the dense entry array grows similarly to a list's backing array. The compact design specifically saved significant memory versus the pre-3.6 layout, since the sparse table now stores small indices instead of full hash/key/value triples per slot.

    Common operations
    • d[key], .get(), .setdefault(), .update(), .pop(), dict comprehensions
    • .keys()/.values()/.items() return live, dynamic views — not copies — that reflect later mutations to the dict
    GotchaMutating a dict's size (adding/removing keys) while iterating over it directly raises RuntimeError: dictionary changed size during iteration — iterate over list(d.items()) if you need to mutate during the loop. Also: keys must be hashable, which is exactly why the immutable types above make good keys and plain list/dict/set don't.
    set
    mutable
    Internal representation

    An open-addressing hash table storing keys only (no associated values) — structurally close to a dict with every value discarded. Unlike dict, set has no guaranteed iteration order — it never adopted the compact/ordered redesign, since ordering isn't part of a set's contract.

    Time complexity
    OperationComplexity
    Add / remove / membershipAverage O(1)
    Union / intersection / differenceRoughly O(len(smaller set))
    Memory layout

    A single sparse hash table array, resized to stay under a target load factor (similar threshold logic to dict, without the second dense array since there's no associated value to keep contiguous).

    Common operations
    • .add(), .remove() (raises KeyError if absent), .discard() (silent if absent), .union()/|, .intersection()/&, set comprehensions
    GotchaIteration order can look stable for small integer sets (because small ints hash to themselves, producing predictable slot placement) — this is a coincidence of the hash function, not a guarantee, and relying on it is fragile the moment other types or larger numbers are involved. Elements must be hashable, exactly as with dict keys.
    bytearray
    mutable
    Internal representation

    The mutable counterpart to bytes — a resizable buffer of raw byte values, using the same dynamic-array-with-over-allocation growth strategy as list, just specialized to store 1-byte values densely instead of full pointers.

    Time complexity
    OperationComplexity
    Indexing, index-assignO(1)
    .append()Amortized O(1)
    .insert() at arbitrary positionO(n)
    Memory layout

    Header + used length + allocated capacity + an inline byte buffer — the same shape as list's layout, just one byte per element instead of one pointer (8 bytes) per element, making it dramatically more memory-efficient for large binary buffers than a list of small ints would be.

    Common operations
    • In-place item assignment (ba[0] = 65), .append(), .extend(), slicing
    • .decode() to get a str; useful for incrementally building binary data without the O(n²) cost that repeated bytes concatenation would incur
    Gotchabytearray is unhashable (like all mutable types) — it can never be a dict key or set member, even though its immutable sibling bytes can. Indexing returns an int, same as bytes.
    The pattern underneath all twelve Every type in this chapter reduces to one of exactly two storage strategies: a contiguous array (int's digits, str's char buffer, tuple/list/bytes/bytearray's element arrays) or a hash table (dict, set, frozenset). Complexity and memory behavior throughout this document — and throughout real Python performance work — almost always traces back to which of these two shapes a given type uses, and whether that structure is fixed-size (immutable) or growable (mutable).
    Chapter 9 — Key takeaways
    • Immutability enables hashability — it's the reason str, tuple, and frozenset can be dict keys and list, dict, and set cannot.
    • Array-backed types (list, tuple, str, bytes, bytearray) give O(1) indexing but O(n) insert/delete away from the end.
    • Hash-table-backed types (dict, set, frozenset) give average O(1) membership and lookup at the cost of no meaningful ordering (set/frozenset) or extra bookkeeping to preserve it (dict).
    • CPython caches small ints (-5..256), interns some strings, and singleton-izes True/False/() — real optimizations, but never something correct code should depend on via is.
    • Repeated string concatenation and repeated list insertion-at-front are the two most common accidental O(n²) patterns in everyday Python code.
    CH. 10Text

    Strings

    Chapter 9 covered str's internal representation. This chapter goes deeper into the text-handling machinery around it: how Unicode and UTF-8 relate, why interning exists, and the practical tools — slicing, formatting, regex, encoding — you'll use on strings constantly.

    Unicode

    Unicode is a universal character standard that assigns every character in (essentially) every writing system a unique number, called a code point, written like U+0041 (the letter "A") or U+1F600 (😀). Since Python 3, every str is a sequence of Unicode code points — there is no separate "ASCII string" type; str always means Unicode text, full stop.

    python3
    s = "café"
len(s)             # 4 -- counts CODE POINTS, not bytes
ord("é")          # 233 -- the code point number
chr(233)          # 'é' -- the inverse

    This is the crucial mental separation for this entire chapter: Unicode is about characters (code points); encodings like UTF-8 are about how those code points are serialized as bytes. A Python str lives entirely in the first world — it has no "encoding" of its own while it exists as a str object in memory (Chapter 9's PEP 393 storage width is an internal implementation detail, invisible at the language level).

    UTF-8

    UTF-8 is the dominant encoding — a specific, reversible rule for turning Unicode code points into a stream of bytes (and back). It is variable-width: ASCII characters (code points 0–127) take exactly 1 byte, and less common characters take 2, 3, or 4 bytes depending on their code point value. This is precisely why the world converged on UTF-8: it's fully backward-compatible with plain ASCII byte-for-byte, while still able to represent every Unicode character that exists.

    python3
    s = "café"
b = s.encode("utf-8")
b                       # b'caf\xc3\xa9'
len(s), len(b)          # 4, 5 -- 'é' is 1 code point but 2 UTF-8 bytes

b.decode("utf-8")      # 'café' -- back to a str
    Gotcha: len() means different things for str vs bytes len(a_str) counts code points; len(a_bytes) counts bytes. They only match when every character happens to be ASCII. This distinction is precisely why string indexing is O(1) (Chapter 9's fixed-width internal storage) while UTF-8 byte-offset indexing into arbitrary characters is not trivially O(1) — you can't jump to "the 5th character" in a raw UTF-8 byte stream without scanning, because characters take a variable number of bytes.

    Interning

    Interning is a memory/speed optimization where multiple, textually-identical strings share one single underlying object instead of each allocating separately — so comparing them can (in the interned case) be a fast identity check rather than a full character-by-character comparison, and memory isn't wasted on duplicates.

    CPython automatically interns:

    • All string literals that look like identifiers — letters, digits, underscores only (e.g. "hello_world", but not "hello world!" with a space and punctuation).
    • Every attribute name, variable name, and keyword-argument name the compiler emits into bytecode (Chapter 3's co_names) — since these are looked up in namespace dicts constantly (Chapter 6), fast identity comparison for hash table lookups matters a great deal here.
    python3
    a = "hello"
b = "hello"
a is b                     # True -- both interned, same object

c = "hello world!"
d = "hello world!"
c is d                     # often False -- not identifier-shaped, not auto-interned

import sys
e = sys.intern("hello world!")
f = sys.intern("hello world!")
e is f                     # True -- forced interning via sys.intern()
    Gotcha Interning is a CPython implementation detail, not a language guarantee — never write code whose correctness depends on is for string comparison; always use ==. Interning is purely a performance optimization operating silently underneath equality comparison.

    Slicing

    String slicing uses the same [start:stop:step] syntax as any sequence, always returning a new string (since strings are immutable, there's no in-place slice):

    python3
    s = "Hello, World!"
s[:5]         # 'Hello'
s[7:]          # 'World!'
s[::-1]        # '!dlroW ,olleH' -- negative step reverses
s[::2]         # 'Hlo ol!' -- every 2nd character

    Slicing never raises an IndexError for out-of-range bounds (unlike single-index access) — it silently clamps to the string's actual length, which is convenient but can mask off-by-one bugs if you're not expecting that leniency.

    Formatting & f-strings

    Python has accumulated three formatting mechanisms; understanding why f-strings won matters as much as the syntax itself:

    StyleExampleNotes
    %-formatting"%s is %d" % (name, age)Oldest, C-printf-inspired; still seen in logging calls and older code
    str.format()"{} is {}".format(name, age)More flexible (named/positional args, nested attribute access); more verbose
    f-stringsf"{name} is {age}"PEP 498 (3.6+); expressions evaluated inline; fastest of the three, because the compiler builds the concatenation logic directly into bytecode rather than parsing a format string at runtime
    python3
    name, age = "Ada", 36
print(f"{name} is {age} years old")
print(f"{age * 2 = }")             # self-documenting: prints "age * 2 = 72"
print(f"{3.14159:.2f}")           # '3.14' -- format-spec after the colon
print(f"{age:>6}")                # right-align in a width-6 field

    Crucially, an f-string is not a runtime-parsed template — the compiler (Chapter 2) parses the embedded expressions at compile time and emits ordinary bytecode to evaluate and concatenate them, which is exactly why f-strings can contain arbitrary Python expressions (function calls, arithmetic, even nested f-strings) and why they outperform the older two styles.

    Regex

    The re module provides regular-expression matching — pattern-based text search, extraction, and substitution, built on its own internal (non-Python-bytecode) regex engine written in C.

    re_demo.py
    import re

pattern = re.compile(r"(\w+)@(\w+)\.com")   # raw string -- avoids escaping backslashes twice

m = pattern.search("contact: ada@example.com")
if m:
    m.group(0)     # 'ada@example.com' -- full match
    m.group(1)     # 'ada'              -- first capture group

re.sub(r"\d+", "#", "room 42, floor 7")   # 'room #, floor #'
re.findall(r"\d+", "room 42, floor 7")      # ['42', '7']
    Performance note re.compile() pre-parses a pattern into an internal matching program once; reusing a compiled pattern object across many calls is faster than passing the raw string to re.search() repeatedly (though the module keeps its own small internal cache of recently-used uncompiled patterns, which softens this in casual one-off use).

    Chapter 10 — Key takeaways
    • Unicode = characters (code points); an encoding like UTF-8 = bytes. A str lives in the first world; a bytes lives in the second — the boundary between them is always an explicit .encode()/.decode() call.
    • UTF-8 is variable-width, which is exactly why len(str) and len(bytes) diverge for non-ASCII text.
    • Interning lets identical identifier-like strings share one object — a real performance detail, never something to rely on with is.
    • F-strings are compiled directly into bytecode, making them both the most readable and the fastest of Python's three formatting styles.
    • Always pass encoding= explicitly when opening files — never rely on the platform default.
    CH. 11Containers

    Collections

    Chapter 9 covered the four built-in containers (list, tuple, dict, set) at the type-internals level. This chapter is about choosing the right one — including the specialized containers in the collections module and the heapq module, each of which exists to make one specific access pattern fast that the built-ins handle poorly.

    Quick recap: list, tuple, dict, set

    ContainerOrdered?Mutable?Best for
    listYesYesSequential data, index access, appending
    tupleYesNoFixed-shape records, dict keys, function returns
    dictYes (insertion)YesKey → value lookup
    setNoYesMembership tests, deduplication, set algebra

    Everything below extends this table with containers that specialize one of these trade-offs further.

    deque

    collections.deque ("deck") is a double-ended queue, implemented internally as a doubly-linked list of fixed-size blocks — not a single flat array like list. That structural choice is the whole point:

    python3
    from collections import deque

dq = deque([1, 2, 3])
dq.appendleft(0)     # O(1) -- would be O(n) on a list!
dq.append(4)         # O(1)
dq.popleft()          # O(1) -- would be O(n) on a list!
dq.pop()              # O(1)

# Bounded deque -- great for "last N items" tracking / sliding windows
recent = deque(maxlen=3)
for i in range(5): recent.append(i)
list(recent)          # [2, 3, 4] -- oldest items silently evicted

    The trade-off: unlike list, random access by index is O(n) on a deque (it has to walk the linked blocks), not O(1). Use deque when you're pushing/popping from either end repeatedly (queues, sliding windows, BFS frontiers); stick with list when you need index-heavy access.

    Counter

    collections.Counter is a dict subclass specialized for counting hashable items — every value defaults to 0 for keys that haven't been seen yet, and it ships with counting-specific convenience methods:

    python3
    from collections import Counter

words = "the quick brown fox the lazy the dog".split()
counts = Counter(words)
counts               # Counter({'the': 3, 'quick': 1, 'brown': 1, ...})

counts["the"]        # 3
counts["nonexistent"]  # 0 -- no KeyError, unlike a plain dict

counts.most_common(2)   # [('the', 3), ('quick', 1)] -- top-N by count

    Internally it's just a dict with an overridden __missing__ hook (returns 0 instead of raising) plus extra methods — no exotic new data structure, just a well-chosen specialization.

    defaultdict

    collections.defaultdict generalizes the same "no KeyError on missing keys" idea to any default value, by taking a zero-argument factory function called automatically the first time a missing key is accessed:

    python3
    from collections import defaultdict

# Grouping pattern -- extremely common real-world use
groups = defaultdict(list)
for name in ["Ann", "Bob", "Al", "Bea"]:
    groups[name[0]].append(name)   # no need to check "is this key here yet?"

dict(groups)          # {'A': ['Ann', 'Al'], 'B': ['Bob', 'Bea']}

    Without defaultdict, the loop body would need if name[0] not in groups: groups[name[0]] = [] before appending — defaultdict removes that boilerplate entirely by calling the factory (list, int, set, or any zero-arg callable) automatically on first access.

    OrderedDict

    collections.OrderedDict predates Python 3.7's guarantee that plain dict preserves insertion order — so today, for plain ordering, a regular dict is sufficient and preferred. OrderedDict still earns its place for a few specific capabilities plain dict doesn't have:

    • .move_to_end(key, last=True/False) — reposition an existing key to either end in O(1), the building block for LRU-cache implementations.
    • Equality comparison is order-sensitive: two OrderedDicts with the same items in different orders compare unequal; two plain dicts with the same items always compare equal regardless of order.
    • Signals intent in an API — makes "this order matters and is part of the contract" explicit and self-documenting, versus a plain dict's order being an implementation nicety.
    python3
    from collections import OrderedDict

od = OrderedDict(a=1, b=2, c=3)
od.move_to_end("a")
list(od)     # ['b', 'c', 'a']

    heapq

    heapq is not a container type at all — it's a module of functions that turn a plain list into a binary min-heap in place, giving O(log n) insertion and O(log n) removal-of-smallest, with the smallest element always sitting at index 0. This is the standard tool for priority queues, "top-K," and merge-style algorithms.

    python3
    import heapq

nums = [5, 1, 8, 2, 9]
heapq.heapify(nums)          # O(n) -- reorders the list in place into heap order
nums[0]                     # 1 -- smallest element, always at the root

heapq.heappush(nums, 0)     # O(log n)
heapq.heappop(nums)          # O(log n) -- removes and returns the smallest

heapq.nsmallest(3, nums)   # the 3 smallest, without fully sorting
    OperationComplexity
    heapify()O(n)
    heappush() / heappop()O(log n) each
    Peek smallest (heap[0])O(1)
    Gotcha heapq only provides a min-heap — for a max-heap, the standard trick is negating values on push and pop (heappush(h, -x)), or wrapping items in a tuple with a negated priority field, since there's no built-in max-heap variant.
    Chapter 11 — Key takeaways
    • deque trades away O(1) random indexing for O(1) operations at both ends — the right choice for queues and sliding windows.
    • Counter and defaultdict both eliminate "check if key exists first" boilerplate; Counter specializes further with counting-specific methods like .most_common().
    • OrderedDict is mostly legacy now that plain dict preserves order, but still earns its keep for .move_to_end() and order-sensitive equality.
    • heapq turns a plain list into an O(log n)-insert, O(log n)-pop-minimum priority queue in place — no dedicated heap type needed.
    CH. 12Expressions

    Operators

    Every operator in Python is, under the hood, a call to a dunder method on an object — a + b is really a.__add__(b) (with a fallback to b.__radd__(a) if the first returns NotImplemented). This chapter groups operators by category and flags the behaviors that differ from most C-family languages.

    Arithmetic operators

    OperatorMeaningDunder
    + - * /Add, subtract, multiply, true divide__add__, __sub__, __mul__, __truediv__
    //Floor division (rounds toward negative infinity, not toward zero)__floordiv__
    %Modulo — result takes the sign of the divisor, unlike C__mod__
    **Exponentiation__pow__
    python3
    -7 // 2     # -4, not -3 -- floors toward negative infinity
-7 % 2      # 1, not -1  -- result matches the sign of the divisor (2)
7 / 2       # 3.5 -- / is ALWAYS true division, even for two ints
    Gotcha for C/Java/JS engineers Python's % is not C-style truncated remainder — it's true mathematical modulo, so negative operands behave differently than most C-family languages. This is deliberate and consistent with // flooring the same direction.

    Logical operators

    and, or, and not — but unlike C-family &&/||, Python's and/or don't return True/False; they return one of the actual operands, using short-circuit evaluation:

    python3
    0 or "default"     # 'default' -- 0 is falsy, so the SECOND operand is returned
"hi" or "default"  # 'hi' -- first operand is truthy, returned as-is, second never evaluated
[] and expensive()  # [] -- short-circuits; expensive() is never called

    This return-the-operand behavior is exactly what powers the common value = user_input or "default" idiom, and why and/or chains are sometimes used as compact conditional expressions (though the explicit x if cond else y ternary is usually clearer).

    Bitwise operators

    OperatorMeaning
    &Bitwise AND
    |Bitwise OR
    ^Bitwise XOR
    ~Bitwise NOT (inverts all bits — for an int x, equals -x - 1, due to two's-complement semantics on Python's conceptually infinite-width integers)
    << >>Left/right shift

    Because int is arbitrary-precision (Chapter 9), bitwise operations conceptually operate on an infinite sign-extended bit pattern rather than a fixed 32/64-bit register — ~5 is -6, not a wrapped-around large positive number the way it might be in a fixed-width language.

    Not just for ints set overloads & | ^ - for intersection/union/symmetric-difference/difference (Chapter 9) — the same symbols, deliberately chosen for the mathematical parallel to set algebra, dispatched via the same dunder-method mechanism as arithmetic.

    Identity & membership operators

    OperatorMeaningComplexity
    is / is notSame object? (Chapter 4) — never overridableO(1) — a single pointer comparison
    in / not inMembership test — calls __contains__O(n) for list/tuple; average O(1) for dict/set/frozenset

    The complexity gap for in is one of the highest-leverage facts in this entire document: checking membership in a list of 100,000 items scans, on average, half of them; the identical check against a set of the same items is a near-constant-time hash lookup. Converting a list to a set before repeated membership tests is one of the single most common, highest-impact optimizations in real Python code.

    Chained comparisons

    Python allows chaining comparison operators in a way that reads like mathematical notation, and — critically — behaves as a single short-circuiting expression, not two separate comparisons joined by and:

    python3
    1 < x < 10              # equivalent to: 1 < x AND x < 10
# but x is only evaluated ONCE, and if "1 < x" is False, "x < 10" is
# never even evaluated -- true short-circuiting, not just sugar

0 <= score <= 100       # classic range-check idiom

a == b == c              # True only if all three are mutually equal
    Gotcha Chained comparisons can produce surprising results with non-transitive-looking expressions: 1 < 2 > 0 is a perfectly valid chain meaning 1 < 2 AND 2 > 0 → True — it's easy to misread as some other operation at a glance if you're not expecting arbitrary comparison operators to chain like this.
    Chapter 12 — Key takeaways
    • Every operator is dunder-method dispatch under the hood — a + b is a.__add__(b), which is precisely how custom classes gain operator support.
    • % and // follow true mathematical flooring, diverging from C-family truncation for negative operands.
    • and/or return operands, not booleans, and short-circuit — the mechanism behind the x or default idiom.
    • in is O(n) on list/tuple but average O(1) on set/dict — one of the most impactful micro-optimizations available in everyday code.
    • Chained comparisons (a < b < c) evaluate the middle term once and short-circuit — not naive sugar for two independent comparisons.
    CH. 13Execution Shape

    Control Flow

    The constructs that decide what runs, in what order, and how many times — including two of Python's less-obvious features: the else clause on loops, and structural pattern matching, both of which have no direct equivalent in most C-family languages.

    if / elif / else

    Standard conditional branching, with one Python-specific nuance: there is no switch statement (until match, below), so long elif chains are the traditional way to express multi-way branching:

    python3
    if score >= 90:
    grade = "A"
elif score >= 80:
    grade = "B"
else:
    grade = "F"

# Ternary / conditional expression -- an expression, not a statement
label = "pass" if score >= 60 else "fail"

    Every branch's truthiness is evaluated via bool() (Chapter 9), which in turn calls __bool__ if defined, or falls back to __len__ (empty containers are falsy), or defaults to truthy for any object defining neither.

    match-case (structural pattern matching)

    PEP 634 (Python 3.10) added match/case — genuinely more powerful than a C-style switch, because it matches on structure and type, not just equality against a single value:

    match_demo.py
    def handle(command):
    match command.split():
        case ["go", direction] if direction in ("n","s","e","w"):
            return f"Moving {direction}"
        case ["take", *items]:
            return f"Taking {', '.join(items)}"
        case ["look"]:
            return "Looking around"
        case _:
            return "Unknown command"

handle("go n")          # 'Moving n'
handle("take sword shield") # 'Taking sword, shield'

    Patterns can also destructure objects by attribute (case Point(x=0, y=0):), match against dict shapes (case {"type": "user", "id": id}:), bind captured values directly into names (direction, items above), and combine conditions with an optional trailing if guard clause. The final case _: is the wildcard — matches anything, conventionally placed last as the "default" case.

    Not just syntax sugar for if/elif match genuinely performs structural matching — checking type, shape, and sub-values simultaneously in one readable pattern — something that would take considerably more nested if/isinstance/indexing logic to express equivalently, which is precisely the readability gap PEP 634 set out to close.

    Loops — for and while

    Python has exactly two loop keywords, and no C-style three-clause for(init; cond; incr) form — for always iterates over an iterable, never a numeric range by default:

    python3
    for item in [1, 2, 3]:      # iterates any iterable -- list, str, dict, generator...
    print(item)

for i in range(5):           # range() is how you get C-style counting
    print(i)

while queue:                # condition checked BEFORE each iteration
    process(queue.pop())

    Under the hood (tying back to Part I), for works by calling iter() on the object to get an iterator, then repeatedly calling next() on it, catching StopIteration to know when to stop — the same protocol powers list comprehensions, generator consumption, and unpacking (Chapter 8).

    break & continue

    break
    Exits the innermost enclosing loop immediately, skipping any remaining iterations entirely — control resumes at the first statement after the loop.
    continue
    Skips the rest of the current iteration's body and jumps straight to the next iteration's condition check (for while) or next item (for for) — the loop keeps running, just this one pass is cut short.
    python3
    for n in range(10):
    if n == 5:
        break          # stop the loop entirely once we hit 5
    if n % 2 == 0:
        continue       # skip even numbers, keep looping
    print(n)           # prints: 1, 3

    Neither keyword has any effect on an outer loop when used inside a nested one — break only escapes the single innermost loop it's lexically inside; breaking out of multiple nested loops at once requires a flag variable, a function-with-return, or restructuring, since Python deliberately has no labeled-break statement.

    else on loops

    This is the single most under-known control-flow feature in Python: for and while loops can have an else clause, which runs if and only if the loop completes without hitting a break. It's best read as "no-break" rather than the "else" the keyword suggests:

    python3
    def has_duplicate(items):
    seen = set()
    for item in items:
        if item in seen:
            print(f"Found duplicate: {item}")
            break
        seen.add(item)
    else:
        # only reached if the loop finished WITHOUT breaking --
        # i.e. no duplicate was ever found
        print("No duplicates found")

    This eliminates a common pattern from other languages where you'd set a boolean flag before the loop, set it inside the if/break branch, and check the flag afterward — for...else collapses all three steps into the loop structure itself. It works identically on while loops (the else runs if the loop's condition became false naturally, not via break).

    pass

    pass is a genuine no-op statement — it does nothing at all, and exists purely to satisfy Python's grammar, which requires every block (if, for, def, class, etc.) to contain at least one statement. It fills a syntactically-required-but-logically-empty block:

    python3
    class CustomError(Exception):
    pass                  # a marker class with no extra behavior needed

def not_implemented_yet():
    pass                  # stub -- fill in later, but keeps the file syntactically valid now

if debug_mode:
    pass                  # deliberately do nothing for now
else:
    log_error()

    It's distinct from both ... (the Ellipsis singleton, sometimes used identically as a stub marker, but is actually an expression producing a real value rather than a statement) and simply leaving a block empty (which is a SyntaxError — Python's indentation-based grammar has no other way to denote an intentionally empty block).

    Chapter 13 — Key takeaways
    • match/case performs genuine structural pattern matching — type, shape, and value simultaneously — not just a value-equality switch.
    • for always iterates an iterable via the iter()/next() protocol; range() is how you opt into C-style counting.
    • break exits the innermost loop only; continue skips to the next iteration; neither has a labeled/multi-level form in Python.
    • for/while...else runs its else block only when the loop finishes without a break — read it as "no-break," and use it to eliminate manual flag-variable patterns.
    • pass is a true no-op that exists solely to satisfy Python's syntax, which never allows a truly empty block.
