    Python Internals — Study Notes

    Part I: How Python Works Internally
    (The Runtime)

    From the moment you press Enter on python app.py to the moment your program produces output — every layer of translation, memory, and machinery in between.

    Goal of this part Build a working mental model of CPython's execution pipeline: how text becomes tokens, tokens become a tree, a tree becomes bytecode, and bytecode becomes running behavior — plus the object model, memory system, scoping rules, and import machinery that every Python program depends on, whether you've ever thought about them or not.
    CH. 01Foundations

    The Python Ecosystem

    Before touching a single opcode, it helps to know what Python actually is — not the syntax, but the project: who built it, why it looks the way it does, and which of the several "Pythons" you are actually running when you type python in a terminal. Almost every internals question later in this document ("why is this slow," "why does this behave oddly") traces back to a decision made in this chapter.

    History of Python

    Python was created by Guido van Rossum and first released in 1991, while he was working at Centrum Wiskunde & Informatica (CWI) in the Netherlands. It grew out of a language called ABC, an educational language Guido had worked on that was elegant but not extensible enough for real systems work. Python kept ABC's readability goals but fixed its extensibility problem by making the language easy to embed and extend using C.

    The name has nothing to do with the snake — Guido was reading scripts from Monty Python's Flying Circus at the time and wanted a name that was short, unique, and slightly irreverent.

    1989–1991
    Guido begins Python as a "hobby" project over the Christmas holidays; first public release, 0.9.0, ships in Feb 1991 — already with classes, exception handling, functions, and the core list/dict/str types.
    1994
    Python 1.0 released. Functional programming tools (lambda, map, filter, reduce) added.
    2000
    Python 2.0 introduces list comprehensions, garbage collection for cycles, and a community-driven development process (PEPs formalized).
    2008
    Python 3.0 released — an intentionally backward-incompatible cleanup (unified str/Unicode model, print() as a function, integer division changes). It was designed without preserving compatibility, which is why the Python 2→3 migration took over a decade.
    2020
    Python 2 reaches end-of-life (Jan 1, 2020). Python 3 becomes the sole actively developed line.
    Today
    Python is steered by the Python Software Foundation (PSF) through a formal proposal process (PEPs — Python Enhancement Proposals), with a yearly release cadence (PEP 602) — one minor version (3.9, 3.10, 3.11 …) per year.
    Why this matters for internals Python's design history explains many "quirks" you'll meet later: dynamic typing and duck typing come from ABC's teaching goals; the C-extension story exists because Guido wanted Python to glue together existing C libraries, not replace them. The interpreter's architecture was never designed for raw speed — it was designed for rapid, readable glue code, and every performance characteristic you'll learn about downstream follows from that founding trade-off.

    Philosophy — The Zen of Python

    PEP 20, written by long-time core developer Tim Peters, encodes Python's design philosophy as 19 aphorisms. It is literally importable:

    >>> import this

    This isn't a poster on a wall — it is enforced, in practice, by the core developers who review every language change. Three lines matter disproportionately for the rest of this document:

    • "Explicit is better than implicit" — is why Python has no implicit variable declarations, no automatic type coercion between incompatible types, and why scoping rules (Chapter 6) require explicit global/nonlocal keywords to mutate outer scope.
    • "There should be one obvious way to do it" — is why Python resists adding redundant syntax, and why the object model (Chapter 4) is unusually uniform: everything is an object, with no special-cased primitives.
    • "Namespaces are one honking great idea" — is a direct preview of Chapter 6 and Chapter 7: Python's entire scoping and import system is built from nothing more exotic than dictionaries mapping names to objects.

    CPython vs PyPy vs Jython vs IronPython

    "Python" is a language specification, not a single program. Multiple independent implementations exist, and they can behave differently at the margins (garbage collection timing, C-extension support, speed). Knowing which one you're running changes what "how Python works internally" even means.

    ImplementationWritten inCompiles toNotable trait
    CPythonCBytecode, run on a stack-based VMThe reference implementation; what "Python" means by default; has the GIL; what this document describes
    PyPyRPython (a restricted, translatable subset of Python)Bytecode → machine code via JITJust-in-time compiled; often 4–10x faster on long-running numeric/loop-heavy code; weaker C-extension compatibility
    JythonJavaJVM bytecodeRuns on the JVM, gives direct access to Java class libraries; no CPython C-extension support; effectively unmaintained for Python 3
    IronPythonC#.NET CLR bytecode (via DLR)Runs on the .NET runtime, interoperates with C#/.NET libraries; Python 3 support arrived late (IronPython 3)
    Insight Every implementation must agree on language semantics (what for loops do, how exceptions propagate, what __init__ means) but is free to choose its own execution strategy. CPython chose "simplest possible correct implementation" — a straightforward tree-walking-turned-bytecode interpreter with manual memory management via reference counting. That choice is why CPython is easy to embed and extend in C, and also why it is not the fastest implementation available.

    Why Python is "interpreted" (historically)

    Calling Python "an interpreted language" is a simplification worth unpacking, because — as you'll see in Chapter 2 — CPython actually compiles your source code before running it. The compilation step just targets a much higher-level, portable bytecode instead of native machine code, and that bytecode is then interpreted by a virtual machine at runtime rather than executed directly by the CPU.

    The "interpreted" label survives for three real reasons:

    1. No separate build step from the user's perspective. You run python app.py directly; there's no explicit "compile, then link, then run" workflow like C or Rust. Compilation to bytecode happens transparently and is cached (Chapter 2).
    2. The compiled artifact (bytecode) is not native machine code. Unlike a C compiler, which emits instructions the CPU executes directly, CPython emits instructions that only CPython's own virtual machine understands — so a second layer of interpretation is unavoidable at runtime.
    3. Late binding, dynamic typing. Types are resolved, attributes are looked up, and even some code paths are decided at runtime rather than compile time — the hallmark of interpreted-language behavior, as opposed to ahead-of-time compiled languages that resolve most of this statically.

    So the accurate mental model is: Python source is compiled to bytecode, and that bytecode is interpreted. "Interpreted language" really describes the second half of that sentence, plus the dynamic, late-bound execution model — not the absence of compilation.

    Why CPython is written in C

    Guido chose C for the reference implementation for pragmatic, not ideological, reasons:

    • Portability. In 1991, a C compiler existed for essentially every platform that mattered. Writing the interpreter in C meant Python could run almost anywhere without a bootstrapping problem.
    • Performance floor. C gives direct control over memory layout and avoids paying for a managed runtime underneath your managed runtime — important because Python itself already adds a large abstraction layer on top.
    • The extension story. Python's core use case from day one was gluing together existing C libraries (numerical code, system libraries, GUI toolkits). Writing the interpreter itself in C meant the exact same ABI and calling conventions could be used to write native extension modules — this is the entire foundation of the C-API (Python.h) and why libraries like NumPy, and CPython built-ins like math, are C code wearing a Python interface.
    • Simplicity of implementation. A straightforward, "reference-counting + tree-of-structs" design in C was achievable by a small team, which mattered enormously for a project without corporate backing in its early years.
    Consequence you'll feel later Because CPython objects are literally C structs (a PyObject* header plus type-specific fields) and reference counting is embedded directly into that struct, CPython gained a straightforward, deterministic memory model (Chapter 5) — but also a global lock around interpreter state, the infamous GIL (Global Interpreter Lock), which exists specifically to keep that C-level reference counting thread-safe without paying for atomic operations on every single refcount change.
    Chapter 1 — Key takeaways
    • Python is a language spec; CPython is the reference implementation — the one this whole document describes.
    • PyPy, Jython, and IronPython trade some compatibility or simplicity for speed or host-platform interop.
    • "Interpreted" really means: compiled to portable bytecode, then interpreted by a VM, with types resolved dynamically at runtime.
    • CPython is written in C for portability, a native performance floor, and — most importantly — to make C-extension development possible using the same object model as the interpreter itself.
    CH. 02Pipeline

    The Execution Pipeline

    This chapter answers the literal question in the Part I goal: what happens between pressing Enter and your program running? CPython moves your source text through six distinct representations before a single line of your logic actually executes.

    01
    Source
    raw .py text
    02
    Lexer
    text → tokens
    03
    Parser
    tokens → CST
    04
    AST
    CST → AST
    05
    Compiler
    AST → bytecode
    06
    PVM
    executes bytecode

    Source code

    Everything starts as a plain text file — a sequence of Unicode characters. CPython first has to figure out the file's encoding (it looks for a # -*- coding: utf-8 -*- style comment on line 1 or 2, per PEP 263; if none is found, it assumes UTF-8). At this stage the file is just bytes/characters — Python has no idea yet what a "function" or "loop" is.

    Lexer & Tokens

    The lexer (also called the tokenizer) scans the raw character stream and groups characters into meaningful chunks called tokens — the smallest units the grammar understands: keywords, identifiers, literals, operators, punctuation, and (uniquely to Python) synthetic INDENT/DEDENT tokens that stand in for Python's significant whitespace.

    You can watch this stage directly with the standard library's tokenize module:

    tokenize_demo.py
    import tokenize, io

src = b"x = 1 if y > 2 else 3\n"
for tok in tokenize.tokenize(io.BytesIO(src).readline):
    print(tok)

# TokenInfo(type=NAME,   string='x',    ...)
# TokenInfo(type=OP,     string='=',    ...)
# TokenInfo(type=NUMBER, string='1',    ...)
# TokenInfo(type=NAME,   string='if',   ...)
# TokenInfo(type=NAME,   string='y',    ...)
# TokenInfo(type=OP,     string='>',    ...)
# TokenInfo(type=NUMBER, string='2',    ...)
# TokenInfo(type=NAME,   string='else', ...)
# TokenInfo(type=NUMBER, string='3',    ...)
# TokenInfo(type=NEWLINE,string='\n',   ...)

    Note that at this point if is just a NAME-class token to the tokenizer, not yet understood as a control-flow keyword — that meaning is only assigned by the parser's grammar rules in the next stage. The lexer's job is purely lexical: it doesn't know or care about grammar, only about "what shape of token comes next."

    Parser, CST & AST

    The parser consumes the flat token stream and imposes structure on it according to Python's formal grammar. Modern CPython (3.9+) uses a PEG parser (Parsing Expression Grammar, PEP 617), replacing the older LL(1) grammar — this is what let Python add tricky-to-parse syntax like the match statement and parenthesized context managers.

    Parsing happens in two conceptual layers:

    CST
    Concrete Syntax Tree — a parse tree that mirrors the grammar exactly, including every token (parentheses, commas, colons). It is a faithful, lossless structural representation of the source text.
    AST
    Abstract Syntax Tree — a simplified tree that keeps only semantically meaningful structure and drops syntactic noise (redundant parentheses, punctuation used only for grouping). This is the tree the compiler actually works from.

    You can inspect the AST directly:

    ast_demo.py
    import ast

tree = ast.parse("x = 1 if y > 2 else 3")
print(ast.dump(tree, indent=2))

# Module(
#   body=[
#     Assign(
#       targets=[Name(id='x', ctx=Store())],
#       value=IfExp(
#         test=Compare(left=Name(id='y', ctx=Load()),
#                       ops=[Gt()],
#                       comparators=[Constant(value=2)]),
#         body=Constant(value=1),
#         orelse=Constant(value=3)))],
#   type_ignores=[])

    Notice how much richer this is than the flat token list — the tree now encodes that this is an assignment, whose value is a conditional expression, whose test is a comparison. This is also the stage where SyntaxError is raised, if your code is grammatically invalid — the AST is only built for grammatically valid programs.

    Where else the AST is used The ast module isn't just for introspection — linters (flake8, pylint), formatters (black), static analyzers (mypy touches a similar typed tree), and code-transformation tools all operate on this same tree structure rather than raw text, because text is ambiguous and the AST isn't.

    Compiler & Bytecode

    CPython's compiler walks the AST and emits bytecode — a low-level, portable instruction set for CPython's own virtual machine. This is a genuine compilation step (source → intermediate representation → target instructions), just like a C compiler emitting assembly — except the "assembly" here targets a software VM instead of a physical CPU. Chapter 3 covers the instruction format itself in depth; for now, see it in its raw form:

    compile_demo.py
    code_obj = compile("x = 1 if y > 2 else 3", "<string>", "exec")
print(code_obj.co_code)      # raw bytes -- the actual bytecode
print(code_obj.co_consts)    # (1, 2, 3, None) -- literal pool
print(code_obj.co_names)     # ('y',) -- global/attr names used

    The compiler's output is a code object — a first-class Python object holding the bytecode itself plus every piece of metadata the VM needs to run it: constants, variable names, the number of local variables, argument info, and more.

    The PVM (Python Virtual Machine)

    The PVM (also called the "eval loop," after its C implementation function _PyEval_EvalFrameDefault) is the last stage: a big loop, written in C, that reads bytecode instructions one at a time and carries out whatever each one says — push a value, call a function, compare two objects, jump to another instruction. It is a stack machine (detailed fully in Chapter 3): almost every instruction pushes to or pops from a per-frame value stack rather than referring to named registers.

    This is the layer that is actually "interpreting" in the traditional sense — it's a software loop simulating a CPU, rather than your source running as native instructions on real silicon.

    __pycache__ and .pyc files

    Compiling source to bytecode has a real, measurable cost, and the bytecode for a given source file doesn't change unless the source does. So CPython caches it: the first time a module is imported, CPython writes the compiled bytecode to a .pyc file inside a __pycache__ directory next to the source. On subsequent runs, if the source file's modification time and size (or content hash, depending on invalidation mode) haven't changed, CPython skips lexing, parsing, and compiling entirely and loads the cached bytecode directly.

    shell
    $ python3 -c "import mymodule"
$ ls __pycache__/
mymodule.cpython-312.pyc
    • The filename encodes the interpreter version (cpython-312) because bytecode is not stable across Python versions — opcodes are added, removed, and renumbered between releases.
    • This caching applies to imported modules, not to the script you run directly with python app.py — the entry-point script is recompiled every run (though everything it imports still benefits from the cache).
    • A .pyc file has a small header (magic number, source hash/timestamp, flags) followed by the marshalled code object — essentially a serialized form of exactly what compile() produces in memory.
    • Deleting __pycache__ is always safe — it's purely a performance cache. CPython regenerates it transparently.
    Try this
    1. Write a small module, import it once, and inspect the generated __pycache__/*.pyc file's timestamp.
    2. Change one comment in the source (no logic change) and re-import — does the .pyc regenerate? (It does — mtime-based invalidation doesn't inspect content, only the timestamp, by default.)
    3. Run python -X importtime app.py to see how much wall-clock time is spent per module import, including compilation.
    Chapter 2 — Key takeaways
    • The pipeline is: source → tokens → CST → AST → bytecode → PVM execution, and it's a genuine multi-stage compiler front end feeding a bytecode interpreter back end.
    • The AST is the real "meaning" of your program as far as the compiler is concerned; tools that analyze Python code almost always work on this tree, not on text.
    • Bytecode is cached in __pycache__/*.pyc per interpreter version so imported modules skip recompilation when unchanged.
    CH. 03The Machine

    Bytecode & The Virtual Machine

    Chapter 2 showed where bytecode comes from. This chapter opens it up: what an instruction actually looks like, how the VM executes it, and why CPython's execution model is described as a stack machine.

    Bytecode & instructions

    Bytecode is a sequence of fixed-format instructions, each consisting of an opcode (what to do) and, for many instructions, an argument (data the opcode needs — an index into a table, a jump target, a count). Since Python 3.6, every instruction is encoded as exactly 2 bytes ("wordcode"): 1 byte opcode + 1 byte argument (instructions needing bigger arguments use EXTENDED_ARG prefix instructions to widen it).

    Crucially, bytecode is not portable across machines in the way "portable" is usually meant for source code — it's portable across operating systems for the same CPython version, but not across CPython versions, and it is meaningless to any other virtual machine. It exists purely as CPython's own internal instruction set.

    Opcodes & the instruction pointer

    Each opcode is a small integer with a symbolic name. A sample of common ones:

    OpcodeMeaning
    LOAD_FASTPush a local variable's value onto the stack
    LOAD_GLOBALPush a global (or builtin) value onto the stack
    LOAD_CONSTPush a constant from co_consts onto the stack
    STORE_FASTPop the top of stack and store it into a local variable
    BINARY_OPPop two values, apply an operator (+, -, *, ...), push the result
    COMPARE_OPPop two values, compare them, push a bool
    CALLPop a callable and its arguments off the stack, call it, push the return value
    POP_JUMP_IF_FALSEPop a value; if falsy, jump the instruction pointer to a target
    RETURN_VALUEPop the top of stack and return it from the current frame

    The instruction pointer (sometimes called the program counter, f_lasti on a frame object) tracks which bytecode instruction executes next. Sequential instructions simply increment it; control flow (if, for, while, function calls) works by setting it to a different offset — exactly analogous to how a CPU's program counter works, just simulated in software instead of hardware.

    The stack machine model

    CPython's VM is a stack machine: instructions don't name their operands (like ADD R1, R2 on a register machine) — they implicitly operate on whatever is currently on top of a per-frame value stack. This makes the instruction set small and simple, at some cost to raw speed compared to register-based VMs (which is part of why PyPy and other high-performance implementations use different execution strategies).

    Trace x = 1 + 2 instruction by instruction:

    after LOAD_CONST 1
    stack[0]1
    after LOAD_CONST 2
    stack[0]1
    stack[1]2
    after BINARY_OP +
    stack[0]3
    (popped 2)— —
    after STORE_FAST x
    stack(empty)
    locals[x]3

    Every value used in an expression briefly lives on this stack. Function calls push a new stack (as part of a new frame — see Chapter 5), so recursion doesn't corrupt the caller's in-progress computation.

    Compiler vs interpreter — where's the line?

    It's worth being precise about terminology, since Chapter 1 already complicated the "Python is interpreted" claim:

    Compiler
    Translates one representation into another without executing it. CPython's compiler translates AST → bytecode. This happens once (or once per source change, thanks to .pyc caching).
    Interpreter
    Executes instructions directly, one at a time, rather than translating them to a lower-level form first. CPython's eval loop interprets bytecode — it doesn't translate it further, it directly carries out each instruction's effect using a giant C switch statement (conceptually) keyed on opcode.

    So CPython is accurately described as a bytecode compiler paired with a bytecode interpreter — both words are correct, they just describe different stages. This distinguishes it from:

    • Pure interpreters (rare in practice) that walk the AST directly with no intermediate instruction format at all.
    • Ahead-of-time compilers (C, Rust, Go) that translate all the way down to native machine code before any execution happens, with no runtime interpretation step left.
    • JIT compilers (PyPy, JavaScript's V8) that interpret at first, then detect "hot" code paths at runtime and compile those specific paths to native machine code on the fly, mixing both strategies.

    The dis module

    The standard library's dis module disassembles bytecode back into human-readable form — the single best tool for building real intuition about what your code costs:

    dis_demo.py
    import dis

def add(a, b):
    return a + b

dis.dis(add)

# 2   0 RESUME     0
#
# 3   2 LOAD_FAST  0 (a)
#     4 LOAD_FAST  1 (b)
#     6 BINARY_OP  0 (+)
#    10 RETURN_VALUE

    Reading this: column 1 is the source line number, column 2 is the byte offset of each instruction, column 3 is the opcode name, and the parenthesized value resolves the raw argument (an index) back to something readable (a variable name, a constant). This is exactly the tool used in Chapter 2's compiler discussion, just applied to a live function object instead of a raw string.

    Practical use dis is how experienced Python engineers answer "which of these two implementations is actually cheaper" without guessing — disassemble both and count instructions, especially CALLs and attribute lookups, which dominate real-world Python overhead far more than arithmetic does.

    Execution flow, end to end

    Putting Chapters 2 and 3 together, here is the complete picture for running python app.py:

    1. CPython's C main() starts up, initializes the runtime (builtins, sys, import machinery).
    2. Your script's source is read and, if not already cached, lexed → parsed → compiled to a code object (Chapter 2).
    3. A frame object is created for the module's top-level code, with its own value stack and local/global namespaces (Chapter 4, 5, 6).
    4. The PVM eval loop begins reading instructions from that code object, one at a time, mutating the stack and namespaces as it goes.
    5. Function calls create new frames (each with its own stack) and transfer control into them; RETURN_VALUE pops the frame and hands a result back to the caller's stack.
    6. When the module-level code reaches its end (or an unhandled exception propagates all the way up), the process exits.
    Chapter 3 — Key takeaways
    • Bytecode instructions are opcode + argument pairs; the VM is a stack machine — operands live on an implicit per-frame stack rather than named registers.
    • CPython is precisely both a compiler (AST → bytecode) and an interpreter (bytecode → effects) — not a contradiction, just two different stages.
    • dis.dis() is the tool for turning "I think this is slow" into "I can see exactly why this is slow."
    CH. 04★ Core Model

    The Python Object Model

    This is the chapter that changes how you read Python code permanently. Nearly every "surprising" Python behavior you've ever hit — mutable default arguments, why a = b doesn't copy, why is and == disagree — is a direct, logical consequence of the model in this chapter. Get this right and the rest of Python stops feeling like a pile of special cases.

    Everything is an object

    In CPython, every single value is an object — not just instances of classes you define, but integers, strings, functions, classes themselves, modules, and even types. There is no category of "primitive" value that lives outside the object system, unlike Java (which has int, double, etc. as non-object primitives) or C.

    python3
    >>> type(5)
<class 'int'>
>>> type(print)
<class 'builtin_function_or_method'>
>>> type(int)
<class 'type'>
>>> type(type)
<class 'type'>   # type is its own type -- the root of the model
>>> (5).bit_length()   # even int literals have methods, because they're objects
3

    Concretely, at the C level, every object is a block of memory that begins with a fixed header — at minimum a reference count and a pointer to a type object (the PyObject struct: ob_refcnt + ob_type). Everything else — an int's digits, a list's internal array, a function's bytecode — is additional data appended after that shared header. This uniform header is precisely what makes the reference counting in Chapter 5 possible: the memory manager only ever needs to understand one struct shape to track the lifetime of any Python value.

    Identity, type, and value

    Every object has exactly three defining properties, and Python exposes a way to inspect each one:

    Identity
    A unique identifier for the object's lifetime, guaranteed stable and unique among simultaneously-alive objects. Exposed via id(obj) — in CPython, this happens to be the object's memory address, though that's an implementation detail, not a language guarantee.
    Type
    Determines what operations the object supports and how it behaves. Exposed via type(obj). An object's type is set at creation and (with rare, deliberately obscure exceptions) never changes.
    Value
    The actual data the object represents. Whether the value can change after creation is exactly the mutable/immutable distinction.

    This gives you two different ways to compare objects, and confusing them is one of the most common real-world Python bugs:

    python3
    a = [1, 2, 3]
b = [1, 2, 3]
c = a

a == b   # True  -- same VALUE (list.__eq__ compares contents)
a is b   # False -- different IDENTITY (two distinct list objects)
a is c   # True  -- same IDENTITY (c is another name for a's object)

    == asks "is the value equal" (and is customizable per-type via __eq__); is asks "is this the literal same object in memory" and can never be overridden. The rule of thumb: use is only for identity-meaningful singletons — None, True, False, and sentinel objects — never for general value comparison.

    Gotcha: small int / short string caching CPython pre-creates and caches small integers (-5 to 256) and some string literals (via interning), so a = 5; b = 5; a is b can return True — not because Python promises this, but because both names happen to point at the same cached object. This is a CPython implementation detail, not a language guarantee, and relying on it is a classic beginner trap.

    Names, bindings & references

    Here is the reframing that unlocks the rest of the chapter: in Python, a name is not a box that holds a value — it is a label in a namespace (Chapter 6) that points at an object living independently on the heap. This is sometimes called "names and bindings" or a "reference model," in contrast to a "value model" like C, where a variable is a fixed chunk of memory that directly stores a value.

    namespace (labels)
    x→ ●
    y→ ●
    heap (objects)
    ● intvalue=3
    ● list[1,2,3]

    The act of x = 3 creates (or reuses) an int object with value 3 somewhere on the heap, and makes the name x in the current namespace point to it. Nothing about the number 3 is "inside" the variable x the way it would be inside a C variable — x is just a pointer with a name attached, stored in a dictionary-like namespace.

    This is exactly why function arguments in Python behave the way they do — often described as "pass by object reference" (or "call by sharing"), distinct from both "pass by value" and "pass by reference" as those terms are used in C++/Java:

    python3
    def mutate(lst):
    lst.append(4)      # mutates the SAME object the caller's name points to

def rebind(lst):
    lst = [9, 9, 9]  # rebinds the LOCAL name only -- caller unaffected

nums = [1, 2, 3]
mutate(nums)
print(nums)     # [1, 2, 3, 4]  -- caller sees the mutation

rebind(nums)
print(nums)     # [1, 2, 3, 4]  -- unchanged; rebind only pointed a LOCAL name elsewhere

    Both lst parameters are bound to the same object the caller's nums is bound to when the function is called — so mutating that object through any name affects everyone pointing at it. But rebinding a name (with =) only ever changes what that one local name points to; it can never reach back and change what the caller's name points to.

    Why Python technically doesn't have "variables"

    The word "variable" implies a fixed storage location whose contents vary. That's an accurate mental model for C, where int x; reserves a specific 4/8-byte slot and assignment overwrites the bytes in that slot. It is not an accurate model for Python.

    The official Python documentation and language reference deliberately avoid the word "variable" in favor of "name" bound in a namespace to an object. This isn't pedantry — the distinction predicts real behavior:

    C-style "variable"Python "name"
    What it isA labeled memory slot with a fixed type and sizeAn entry in a namespace dict, pointing to an object
    AssignmentOverwrites the bytes at that memory locationRepoints the label at a (possibly brand-new) object; old object is untouched
    TypeBelongs to the variable, fixed at declarationBelongs to the object, not the name — the same name can point to an int, then a string
    Two names, one valueRequires an explicit pointer/referenceThe default — any two names can point at the same object with plain =

    This is also why Python is described as dynamically typed: x = 5; x = "hello" is completely legal, because typing is a property of the object x currently points to, not of x itself. The name has no type of its own — it is just a label that can be moved to point at any object at any time.

    Assignment & multiple references

    = in Python is always a binding operation, never a copy operation. This holds regardless of what's on the right-hand side:

    python3
    a = [1, 2, 3]
b = a                # b now points at the SAME list object as a -- no copy made
b.append(4)
print(a)             # [1, 2, 3, 4] -- a "sees" it too, because there was only ever one list

print(id(a) == id(b))   # True -- confirms same object

    To get an actual independent copy, you must ask for one explicitly — again, "explicit is better than implicit" from the Zen:

    python3
    import copy

shallow = a.copy()          # or list(a), or a[:]  -- new outer list, same inner objects
deep    = copy.deepcopy(a)  # new outer list AND recursively new inner objects

    Multiple references to one object are the normal, cheap, default case in Python — this is precisely what makes reference counting (Chapter 5) the right memory strategy: the runtime needs to know exactly how many names/containers are pointing at each object, because that's what determines when it's safe to free.

    Object lifetime

    An object's lifetime is bounded by two events: creation (when it's constructed — a literal is evaluated, a constructor is called, an operation produces a new result) and destruction (when nothing references it anymore, so CPython reclaims its memory). Chapter 5 covers destruction mechanics (reference counting, the cyclic garbage collector) in full detail — for now, the object-model-level point is:

    • An object stays alive exactly as long as at least one reference to it exists — from a name, a container, another object's attribute, or an internal reference held by the interpreter itself (like a currently-executing frame's stack).
    • Rebinding a name, deleting it (del x), a container going out of scope, or a frame returning all remove a reference — they don't necessarily destroy the object, only if that was its last reference.
    • You never manually free a Python object the way you'd call free() in C — you only ever remove references to it, and the runtime decides when zero references means "safe to destroy."
    If names aren't variables, why does everyone (including Python's own docs) still say "variable" casually?
    Because it's a harmless shorthand once you understand the underlying model — the danger is only in taking the C-style mental model literally when reasoning about mutation, aliasing, or default arguments. This document uses "name" when precision matters and "variable" as loose shorthand elsewhere, exactly like most experienced Python engineers do.
    Does this reference model make Python slower than a value model like C?
    There's real overhead — every "variable access" is a pointer dereference plus (for attribute/global lookups) a dictionary lookup, versus a direct memory read in C. This is one of several compounding reasons CPython is slower than compiled languages for equivalent raw computation, alongside dynamic typing and bytecode interpretation (Chapter 3).
    Chapter 4 — Key takeaways
    • Everything is an object — a PyObject header (refcount + type pointer) plus type-specific data, uniformly, with no unboxed primitives.
    • A name is a label in a namespace pointing at an object — not a storage slot. Types belong to objects, not names.
    • = always binds a name to an (existing or new) object; it never copies. Two names can cheaply share one object, which is why mutation through one name is visible through the other.
    • is compares identity (same object); == compares value (customizable per type). They agree far less often than beginners assume.
    • Object lifetime = as long as at least one reference exists; how that's tracked and enforced is the subject of Chapter 5.
    CH. 05Lifecycle

    Memory Management

    Chapter 4 established that objects live independently on the heap and are reached through references. This chapter covers the machinery that actually tracks those references and decides when memory can be reclaimed — the mechanics behind "object lifetime."

    Heap vs stack (two different stacks, don't confuse them)

    There are genuinely two different "stacks" relevant to a running Python program, and conflating them causes real confusion:

    C call stack
    The operating-system-level stack used by the CPython interpreter's own C function calls (e.g. _PyEval_EvalFrameDefault calling itself recursively for nested Python calls). This is what limits deep Python recursion — sys.setrecursionlimit() exists mainly to fail with a clean RecursionError before this C stack actually overflows and crashes the process.
    Python value stack
    The per-frame stack introduced in Chapter 3 — a data structure the bytecode interpreter pushes/pops operands onto while evaluating expressions. It lives inside a frame object, which itself lives on the heap.
    The heap
    Where essentially all Python objects actually live — ints, lists, strings, function objects, frame objects, everything from Chapter 4. There is no Python-level equivalent of C's automatic stack-allocated local variables; every object, no matter how small or short-lived, is a heap allocation from the object model's point of view.

    So when a Python function runs, a new frame object (heap-allocated) is created holding a new value stack (also effectively heap-backed), and this all happens underneath a C function call that itself uses the real, OS-level C stack. Three layers, easy to conflate, genuinely distinct.

    Reference counting

    CPython's primary memory management strategy is reference counting: every object's header (Chapter 4) stores an integer, ob_refcnt, counting how many references currently point to it. The count is incremented every time a new reference is created (a name binding, appending to a list, passing as an argument) and decremented every time a reference goes away (rebinding, del, a container being cleared, a frame returning).

    python3
    import sys

x = []
print(sys.getrefcount(x))   # 2 -- one for 'x', one for the temporary arg to getrefcount() itself

y = x
print(sys.getrefcount(x))   # 3 -- 'x', 'y', and the temporary arg

del y
print(sys.getrefcount(x))   # back to 2

    When the count reaches zero, CPython knows — deterministically, immediately, with no scanning or delay — that nothing can reach the object anymore, and frees it right there. This is why Python's memory cleanup is largely deterministic: unlike a tracing-only garbage collector (as in Java or Go), you can often predict the exact moment an object's __del__ runs, because it's tied to the precise statement that drops the last reference, not to an unpredictable GC cycle.

    Why this is also why the GIL exists Incrementing/decrementing a plain integer isn't safe if two threads could do it simultaneously — you'd get lost updates and either premature frees or memory leaks. CPython's Global Interpreter Lock exists largely to guarantee only one thread executes bytecode (and therefore touches refcounts) at a time, sidestepping the need for expensive atomic operations on every single reference count change, everywhere, throughout the interpreter.

    The garbage collector (cyclic GC)

    Reference counting has exactly one structural blind spot: reference cycles. If object A references object B, and B references A, their counts never reach zero through normal dereferencing — even if nothing outside the cycle can reach either of them anymore.

    CPython solves this with a secondary, generational, tracing garbage collector (the gc module) that runs periodically alongside reference counting, specifically to find and collect these unreachable cycles. It only needs to track objects that are capable of participating in a cycle — meaning "container" types that can hold references to other objects (lists, dicts, class instances, etc.); plain immutable scalars like ints and strings are exempt because they can never point back at anything.

    • It organizes tracked objects into three generations (0, 1, 2) based on survival — new objects start in generation 0; if a collection pass doesn't free them, they get promoted, on the empirical assumption ("generational hypothesis") that most objects die young, so scanning young objects frequently and old objects rarely is an efficient trade-off.
    • Collection is triggered automatically based on allocation/deallocation thresholds, and can also be run manually with gc.collect().
    • It can be disabled entirely with gc.disable() — sometimes done deliberately in latency-sensitive short-lived processes, relying purely on reference counting plus process exit to reclaim memory.

    Cyclic references, in practice

    python3
    class Node:
    def __init__(self):
        self.other = None

a = Node()
b = Node()
a.other = b     # a references b
b.other = a     # b references a -- a cycle

del a
del b
# Neither refcount ever hit zero -- each still holds one reference
# from the other. They are unreachable from anywhere else in the
# program, but pure refcounting alone will never free them.
# The generational cyclic GC is what eventually finds and frees this pair.

    The most common real-world source of accidental cycles is a parent object holding a reference to a child, and that child holding a "back-reference" to its parent (common in tree/graph structures, GUI widget hierarchies, and ORMs) — almost always intentional and harmless, because the cyclic GC handles it, just with a small delay compared to pure refcounting.

    id() and del, precisely

    id(obj) returns an object's identity — in CPython specifically, its memory address, though the language only guarantees it's a stable, unique-among-simultaneously-alive-objects integer for the object's lifetime; treating it as a memory address is a CPython-specific detail.

    del name is frequently misunderstood as "delete the object." It does not — del removes a name from its namespace, which decrements the refcount of whatever object that name pointed to. The object is only actually destroyed if that was its last reference.

    python3
    a = [1, 2, 3]
b = a
del a         # removes the NAME 'a'; the list itself is untouched -- b still holds it
print(b)     # [1, 2, 3] -- still fully alive

    Weak references

    A normal reference keeps its target alive. A weak reference (weakref module) lets you refer to an object without increasing its refcount — meaning the object can still be garbage collected as if the weak reference didn't exist. This is the tool of choice for caches, observer patterns, and any parent↔child relationship where you want to avoid manufacturing an artificial reference cycle in the first place.

    weakref_demo.py
    import weakref

class Cache: pass

obj = Cache()
ref = weakref.ref(obj)    # does NOT bump obj's refcount

print(ref())            # <Cache object> -- call it to get the real object (or None if dead)

del obj
print(ref())            # None -- the object was freed; the weak ref doesn't keep it alive

    weakref.WeakValueDictionary and WeakKeyDictionary build on this to make entire caches whose entries disappear automatically the moment nothing else references them — no manual eviction logic required.

    Try this
    1. Create a deliberate reference cycle, call gc.disable() first, and watch gc.collect() report the count of unreachable objects it finds when you re-enable and run it manually.
    2. Implement __del__ on a class and observe exactly when it fires relative to del statements, function returns, and reassignment — this builds real intuition for refcount-driven lifetime.
    3. Use tracemalloc to snapshot memory before/after a loop that (accidentally) keeps appending to a module-level list, and see the leak show up concretely.
    Chapter 5 — Key takeaways
    • Three distinct "stacks/spaces" exist: the OS-level C call stack, the per-frame Python value stack, and the heap where all objects actually live.
    • Reference counting is the primary, deterministic memory strategy — an object is freed the instant its refcount hits zero.
    • The cyclic GC is a secondary, periodic, generational collector that exists solely to catch reference cycles, which refcounting alone can never resolve.
    • del removes a name binding, not an object — destruction only follows if that was the object's last reference.
    • Weak references let you observe an object without keeping it alive — the standard tool for caches and back-references.
    CH. 06Lookup Rules

    Namespaces & Scope

    Chapter 4 established that a name is a label in a namespace. This chapter answers the natural follow-up: when your code says x, which namespace does Python actually search — and in what order?

    The LEGB rule

    Every name lookup in Python is resolved by searching, in this exact order, until a match is found: Local → Enclosing → Global → Builtin. If none of the four contain the name, Python raises NameError.

    Local (L)
    Names assigned anywhere inside the current function — including ones that haven't executed yet — belong to that function's local namespace. This is determined statically by the compiler scanning the function body at compile time, not dynamically as the function runs.
    Enclosing (E)
    The local namespace of any enclosing function, for nested functions — this is what makes closures possible. Skipped entirely for top-level functions with no enclosing function.
    Global (G)
    The module-level namespace — every name assigned at the top level of a .py file, outside any function or class body.
    Builtin (B)
    Names Python provides automatically to every module — print, len, range, Exception, and dozens more — living in the builtins module, checked only after all three narrower scopes miss.
    legb_demo.py
    x = "global"        # Global scope

def outer():
    x = "enclosing"    # Enclosing scope (relative to inner())

    def inner():
        x = "local"    # Local scope
        print(x)        # "local"     -- found at L, search stops immediately

    inner()
    print(x)          # "enclosing" -- outer()'s own local x

outer()
print(x)              # "global"    -- module-level x, untouched by either function
print(len)             # <built-in function len> -- found only at B, since 'len' is never assigned above

    The critical, often-surprising rule: if a name is assigned anywhere in a function body, Python treats it as local for the entire function — even on lines that execute before the assignment. This is a compile-time decision, not a runtime one, and it produces a classic bug:

    python3
    count = 0

def increment():
    print(count)    # UnboundLocalError, NOT 0!
    count = count + 1  # this assignment makes 'count' local for the WHOLE function
    # Python sees the assignment on line 2 at compile time, decides 'count'
    # is local everywhere in this function -- so the print() above tries to
    # read a local 'count' that hasn't been assigned yet, and fails.

    The global keyword

    Per the Zen's "explicit is better than implicit," Python never lets a plain assignment inside a function silently rebind a global name — it always creates a new local instead (as just demonstrated). To deliberately rebind a module-level name from inside a function, you must declare intent explicitly with global:

    python3
    count = 0

def increment():
    global count     # explicit: 'count' here means the module-level name
    count = count + 1

increment()
print(count)          # 1 -- the module-level name was actually rebound

    Note: global is only needed for assignment. Merely reading a global name (with no assignment anywhere in the function) works fine without it — LEGB finds it at the G step naturally. global is also unnecessary for mutating a global object in place (e.g. some_global_list.append(x)) — that's a method call on an object you already have a reference to via lookup, not a rebinding of the name itself.

    The nonlocal keyword

    nonlocal solves the identical problem one level up: rebinding a name that lives in an enclosing function's scope (not global, not local) — most commonly needed inside closures:

    python3
    def make_counter():
    count = 0
    def increment():
        nonlocal count   # explicit: this 'count' means make_counter's local, not a new local
        count += 1
        return count
    return increment

counter = make_counter()
print(counter())   # 1
print(counter())   # 2 -- state persists across calls, held alive by the closure

    Without nonlocal, count += 1 inside increment() would raise UnboundLocalError for exactly the same reason as the global example — the assignment makes count local to increment(), shadowing the enclosing one, before the read on the right-hand side of += can even happen. nonlocal can reach through any number of nested enclosing functions, but — unlike global — it cannot reach all the way to module (global) scope; it's specifically for enclosing function scopes.

    Module & function namespaces, concretely

    Namespaces aren't an abstract concept — they are, quite literally, dictionaries mapping name strings to objects, and Python exposes them directly:

    FunctionReturns
    globals()The current module's namespace dict — same object as module.__dict__
    locals()The current local namespace as a dict (a live view at module/class scope; a snapshot copy inside a function, for CPython implementation reasons)
    vars(obj)An object's own __dict__, if it has one — instances, modules, classes
    dir(obj)A sorted list of names reachable from obj, including inherited ones — a readability helper, not the raw namespace itself
    python3
    x = 42
print("x" in globals())   # True -- module namespace really is just a dict
print(globals()["x"])       # 42 -- can even read a name by string key, bypassing normal syntax

    This is precisely why Chapter 4's "namespaces are one honking great idea" quote and Chapter 7's import system connect so tightly: a module object, at its core, is barely more than a namespace dict with a name attached — import is largely about creating one of these and making it reachable, which is exactly where the next chapter picks up.

    Chapter 6 — Key takeaways
    • LEGB — Local, Enclosing, Global, Builtin — is the fixed search order for every name lookup, resolved statically by the compiler for the Local/Enclosing layers.
    • Any assignment anywhere in a function body makes that name local for the entire function, which is the root cause of most UnboundLocalErrors.
    • global and nonlocal exist purely to make rebinding an outer name an explicit, deliberate act — reading and in-place mutation never need them.
    • Namespaces are literally dictionaries — globals(), locals(), and __dict__ expose them directly, and this is the same machinery the import system builds on.
    CH. 07Modularity

    The Import System

    The final piece of the runtime picture: how import actually works, why it's safe to import the same module from ten different files without ten times the cost, and why circular imports break in the specific way they do — all direct consequences of Chapters 2 and 6.

    Modules & packages

    Module
    The unit of code reuse — in the simplest case, just one .py file. When imported, Python executes the file top to bottom exactly once and wraps the resulting namespace (Chapter 6) in a module object.
    Package
    A directory containing modules (and/or sub-packages), used to organize larger codebases hierarchically. A package is really just a module whose namespace happens to be built from a directory instead of a single file.

    import mypkg.mymodule works because Python's import machinery translates dotted names into a filesystem/package search: it looks for a mypkg package, then a mymodule inside it, following the mechanisms below.

    __init__.py

    __init__.py is the file that (historically) marks a directory as a package and runs automatically the first time that package (or anything inside it) is imported. Its responsibilities, in practice:

    • Runs package-level setup code — the same way a module's top level runs on first import.
    • Controls what a plain from mypkg import * exposes, via an explicit __all__ list.
    • Commonly re-exports selected names from submodules, so users can write from mypkg import Thing instead of from mypkg.submodule import Thing — a deliberate public-API decision, not an accident.
    Modern nuance Since PEP 420 (Python 3.3+), a directory without an __init__.py can still function as a namespace package — useful for splitting one logical package across multiple distributed directories. A directory with __init__.py is called a regular package and remains the overwhelmingly common, more explicit choice for ordinary projects.

    Import caching & sys.modules

    This is the single most important mechanical fact about imports: sys.modules is a dictionary that caches every module that has ever been imported, keyed by its full dotted name. Every import statement, anywhere in your program, checks this cache first.

    python3
    import sys
import json

"json" in sys.modules       # True -- it's cached now
sys.modules["json"] is json   # True -- literally the same module object

import json as j2
j2 is json                  # True -- re-importing hands back the cached object, doesn't re-run the file

    This is what makes import cheap after the first time, and — more importantly — guarantees a critical correctness property: a module's top-level code runs exactly once per process, no matter how many files import it. Every importer receives a reference to the same module object, sharing the same namespace — module-level state (a cache dict, a singleton, a database connection pool) is genuinely shared across your whole codebase for free, because of this cache.

    The actual algorithm, simplified, when you write import foo:

    1. Is "foo" already a key in sys.modules? If yes, bind the name foo to that cached object and stop — no file is re-read or re-executed.
    2. If not, search sys.path (a list of directories) for a matching module or package using the configured finders and loaders (the importlib machinery).
    3. Once found, create a new, initially-empty module object and insert it into sys.modules immediately — before executing a single line of its code. This early insertion is precisely what makes circular imports partially work, and is the key to understanding the next section.
    4. Execute the module's code top to bottom, populating its namespace as it goes.
    5. Bind the name in the importing scope.

    Circular imports

    A circular import happens when module A imports module B, and module B (directly or transitively) imports module A back. Given step 3 above — the module is registered in sys.modules before it finishes executing — a circular import doesn't always crash, but it does mean the "back-importing" module can receive a partially initialized module object, one that's missing whatever names haven't been defined yet at that point in execution.

    a.py
    import b
def func_a(): return "a"
    b.py
    import a
print(a.func_a())   # AttributeError!
# When b.py runs (triggered from inside a.py's own "import b" line),
# a's module object already exists in sys.modules -- but a.py hasn't
# gotten past its own "import b" line yet, so func_a isn't defined
# on it yet. b gets a real but incomplete version of module a.

    Common fixes, in order of general preference:

    • Restructure — move the shared functionality both modules need into a third module they both import from, avoiding the cycle entirely (usually the right long-term fix).
    • Import inside the function, not at module top level — delays the import until the function is actually called, by which point both modules have finished their top-level execution.
    • Import the module, not the name — import a then use a.func_a() at call time, rather than from a import func_a at the top, since the latter needs the name to exist at import time, while the former only needs the attribute to exist by the time you actually call it.

    Relative vs absolute imports

    Absolute import
    import mypkg.utils or from mypkg.utils import helper — specifies the full dotted path from a top-level entry on sys.path. Unambiguous, doesn't depend on the importing file's own location, and is the style recommended by PEP 8 for most cases.
    Relative import
    from . import sibling or from ..otherpkg import thing — expressed relative to the current module's own position inside its package, using leading dots (one dot = current package, two dots = parent package, and so on). Only legal inside a package (a file that has a real __package__), never in a standalone top-level script.

    Relative imports are resolved using the module's __name__/__package__ attributes, not the filesystem path directly — which is exactly why running a file inside a package directly as a script (python mypkg/module.py) often breaks its relative imports: run that way, Python sets __name__ = "__main__" and has no package context to resolve the dots against. Running it as python -m mypkg.module instead preserves the package context and fixes this.

    Try this
    1. Add a print("loading X") at the top of a module, import it from three different files in the same run, and confirm the print only fires once — direct proof of the sys.modules cache.
    2. Deliberately construct the two-file circular import example above and reproduce the AttributeError; then fix it using the "import the module, not the name" pattern.
    3. Compare python mypkg/mod.py vs python -m mypkg.mod when mod.py contains a relative import, and observe the difference firsthand.
    Chapter 7 — Key takeaways
    • sys.modules caches every imported module by dotted name — a module's top-level code runs at most once per process, and every importer shares one namespace.
    • A module is registered in the cache before it finishes executing, which is both why some circular imports work at all and exactly why others fail with a partial-attribute error.
    • __init__.py marks (and initializes) a regular package; namespace packages (no __init__.py) are a more specialized, PEP 420 alternative.
    • Prefer absolute imports; reach for relative imports deliberately within a package, and remember they depend on package context, not raw file location.
